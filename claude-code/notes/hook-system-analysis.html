Claude Code Hook 系统

生命周期驱动的插件框架 — 27 个 Hook 事件 × 4 种执行类型

Summary

Hook 系统是 Claude Code 的生命周期插件框架。它在 CLI 运行的各个关键节点触发用户/插件定义的钩子，允许外部代码介入、审核和增强 Claude Code 的行为。

一句话定位：Hook 系统 = 可编程的中间件管道，在 Claude Code 生命周期的 27 个节点上并行执行用户配置的脚本/LLM 调用/HTTP 请求。

四种执行载体覆盖不同场景：

  • command Shell 脚本 —— 本地文件检查、git hooks、CI 触发
  • prompt LLM 单次调用 —— 快速语义验证（Haiku 默认）
  • agent LLM 多轮代理 —— 复杂验证需要读写文件、运行命令
  • http HTTP POST —— 通知外部系统、对接企业审批流

Hook 配置来源有清晰的优先级层级，通过 settings.json 的多层级合并 + 去重机制，保证策略可控、无重复执行。所有 hook 并行执行，通过退出码/JSON 输出协议与 Claude Code 交互。

Use Cases: 为什么选择 Hook 系统？

Hook 系统不是唯一的自动化方案——你可以手动执行脚本、写 cron job、或者靠 CI 流水线。但以下场景中，hook 系统提供了不可替代的价值：它的执行时机恰好处于 Claude Code 的生命周期关键节点，拥有完整的上下文信息，能以最低延迟介入决策。

UC1: 安全网关 — 在工具执行前拦截危险操作

场景：防止 Claude Code 执行危险命令（rm -rf / 等）或写入敏感路径。

问题：内置的权限系统（PermissionMode）只做简单 allow/deny/ask。但它不知道"这个命令在今天的上下文中是否安全"——一个脚本在测试时是安全的，在生产目录中可能就不行。

为什么用 Hook 系统？

PreToolUse hook 在工具即将执行但尚未执行时触发，这意味着：

  • Hook 拥有完整的工具调用上下文（参数 + 当前工作目录 + 会话状态）
  • 可以执行任意复杂的检查——比内置权限规则更灵活
  • 可以返回 block 决策阻止执行，也可以修改输入参数后放行
  • 实时性：在危险操作生效前拦截，而不是事后审计发现

替代方案的缺陷：Cron job 做不到实时拦截；手动审核依赖人的注意力；内置权限规则不够灵活。只有 hook 站在了"刚好在危险发生前"这个时间窗口。

UC2: 团队规范强制执行 — 代码格式化与质量门禁

场景：每次 Write/Edit 后自动格式化代码、检查是否有调试代码遗留（console.log 等）。

问题：CI 流水线可以发现这些问题，但反馈周期太长——开发者已经切换到下一个任务了。而且 CI 不总能修复格式问题，只能报错。

为什么用 Hook 系统？

PostToolUse hook 在工具执行完毕后触发，此时：

  • 知道刚刚修改了哪个文件（通过 $CLAUDE_TOOL_INPUT_FILE_PATH）
  • 可以直接修改文件内容（格式化、替换占位符）
  • 即时反馈：在 Claude 继续输出之前，代码已经被修复好了
  • 格式修改自动纳入会话上下文，不会丢失

替代方案的缺陷：IDE 的 save-on-format 不覆盖 Claude Code 的写入；CI 只能报错不能自动修复；pre-commit hook 只能拦截 git commit 阶段。Hook 在每次文件变更时立即且自动处理。

UC3: 企业合规审批 — 对接外部审批流

场景：高风险操作（如生产数据库写入、部署到生产环境）需要经过外部合规系统审批。

问题：Claude Code 的权限系统只有 allow/deny/ask 三种决策。但企业合规需要多方审批、有审批超时、需要记录审计日志。

为什么用 Hook 系统？

PermissionRequest hook 在权限弹窗出现时触发，而且支持 HTTP hook 类型：

  • 可以将审批请求 POST 到企业审批系统（如 ServiceNow、Jira）
  • HTTP 响应可以返回 allow、deny 或 ask（交给用户判断）
  • 完整的 SSRF 防护和白名单机制保证安全
  • 审计日志在企业端集中管理

替代方案的缺陷：内置权限系统不支持外部审批流；手动找领导签字太慢且不系统化；构建独立的审批网关需要维护额外的基础设施。Hook 是 Claude Code 与外部系统之间的原生集成点，零额外架构。

UC4: 动态上下文注入 — 让 Claude "知道"项目状态

场景：每次启动会话时，自动注入当前 git 分支、未提交变更、待办事项。

问题：用户需要手动告诉 Claude 当前项目状态，容易遗漏或描述不准确。CLAUDE.md 是静态的，无法捕捉实时状态。

为什么用 Hook 系统？

SessionStart hook 在会话启动时触发，此时：

  • 可以通过 startup source 匹配初始启动（区别于 resume）
  • 可以执行命令获取当前 git status、branch、环境变量
  • 通过 additionalContext 或 initialUserMessage 注入给模型
  • 注入的内容是实时状态，不是静态文本

替代方案的缺陷：手动粘贴状态信息容易出错；CLAUDE.md 不支持动态内容；preload 脚本无法与 Claude Code 的会话系统集成。Hook 让注入自动、准确、实时。

UC5: 完整变更审计 — 记录一切操作

场景：合规团队需要审计所有文件修改和命令执行记录。

问题：CLI 日志记录了输出，但缺少结构化信息——不知道哪些文件被改了什么、命令的精确参数是什么。

为什么用 Hook 系统？

PostToolUse hook 在多维度提供审计数据：

  • 知道具体写入的文件路径和内容（通过工具输出）
  • 可以记录到结构化格式（JSON log、数据库、外部系统）
  • 可以区分不同工具类型分别处理（Read 不记录，Write/Edit 详细记录）
  • 所有 hook 并行执行，不影响主线流程性能

替代方案的缺陷：shell script 命令记录的是原始终端输出，没有结构化信息；CLI --verbose 日志缺少工具参数的语义信息；单独写监控脚本需要解析 stdout，脆弱且不完整。Hook 在数据产生的精确位置捕获结构化数据。

UC6: 子代理管道编排 — 多步骤工作流自动衔接

场景：需要依次执行 PM 规划 → 架构设计 → 编码实现 → 代码审查的流水线。

问题：手动编排子代理需要用户不断在中间切换角色，流程冗长且容易中断。

为什么用 Hook 系统？

SubagentStop hook 在子代理完成时触发，配合 Stop hook 形成可靠的接力链：

  • 可以读取子代理的输出文件，判断下一步该做什么
  • 通过 additionalContext 向模型建议下一步操作
  • 每个阶段的上下文完整传递给下一步
  • 不需要额外的流程引擎——hook + agent 就是工作流引擎

替代方案的缺陷：第三方工作流引擎（Temporal、Airflow）太重，不适合开发工具场景；手动编排容易遗漏步骤；固定脚本无法根据上一步输出动态决定下一步。Hook 提供了轻量级、可编程的流程衔接机制。

UC7: 文件变化自动响应 — 监听外部变更

场景：当外部进程修改了项目文件（如设计师改动了 design tokens），自动通知 Claude 刷新认知。

问题：Claude 是对话驱动的，不知道外部世界发生了什么变化，除非用户告诉它。

为什么用 Hook 系统？

FileChanged hook 结合 SessionStart 中的 watchPaths：

  • 在会话开始时注册要监控的文件路径
  • 文件变更时自动触发 hook，获取变更内容
  • 变更内容通过 additionalContext 注入给模型
  • 不需要轮询、不需要手动通知

替代方案的缺陷：用户手动刷新依赖注意力和记忆力；cron job 轮询浪费资源且延迟不可控；外部 watcher 无法与 Claude 的上下文系统通信。Hook 是文件系统事件和 LLM 上下文之间的桥梁。

总结：Hook 的核心优势

维度Hook 系统替代方案
上下文完整性 拥有完整的会话上下文（工具参数、执行结果、会话状态） cron job / 独立脚本无法获取
CLI 日志只有 stdout 输出
实时性 事件发生时零延迟触发 cron 分钟级延迟
CI 分钟级延迟
双向交互 可修改输入、阻止执行、注入上下文、决定权限 webhook 单向通知

零额外架构 平台内置，配置即用 需要额外部署服务、维护队列、管理状态

一句话总结：Hook 系统最适合那些需要在正确的时间、拥有完整的上下文、立即做出反应的场景。它填补了"内置功能不够用"和"自己搭一套太重"之间的空白。

3. Hook 系统是做什么的？

Hook 系统让用户在 Claude Code 的关键生命周期节点插入自定义逻辑，实现：

能力典型场景
工具审核 PreToolUse hook 在 Bash/Write 执行前检查命令安全性，阻止危险操作
权限扩展 PermissionRequest hook 实现自定义审批流程（如企业合规系统）
上下文注入 SessionStart hook 自动注入项目规范、动态 system prompt
事后审计 PostToolUse hook 记录所有文件编辑、命令执行到外部日志系统
会话生命周期 SessionEnd hook 清理临时文件、上报会话统计
通知集成 Notification hook 在任务完成/空闲时发送桌面通知或 Slack 消息
文件监控 FileChanged hook 监听外部文件变更并自动响应
插件扩展 WorktreeCreate/Remove hooks 让插件介入 VCS 工作树管理

本质：Hook 是 Claude Code 的 "中间件" —— 在每个关键节点，所有匹配的 hook 并行执行，结果按优先级规则合并，决定后续行为（允许/阻止/询问）。

4. 有哪些地方可以做 Hook？

Claude Code 定义了 27 个 Hook 事件，覆盖完整生命周期。每个事件有特定的匹配字段（matcher），允许精细化控制 hook 触发条件。

4.6 Matcher 匹配规则

每个 HookMatcher 包含可选的 matcher 字段，决定哪些场景触发：

写法含义示例
精确匹配完全等于"Write" 仅匹配 Write 工具
管道符列表匹配任意一个"Edit|Write" 匹配 Edit 或 Write
正则表达式按正则匹配"Bash|Edit|Write"
空 / 不设置匹配全部对该事件的所有触发都执行

额外过滤：if 字段支持权限规则语法做更精细的条件匹配，例如 "if": "Bash(git *)" 仅在 Bash 命令匹配 git * 时触发，避免不必要的进程启动。

5. 内置了哪些 Hook？

Claude Code 内置了三类 hook，注册为 internal: true 的 callback hook，不展示给用户，不走用户 hook 的分析统计：

5.1 会话文件访问追踪 sessionFileAccessHooks

文件：src/utils/sessionFileAccessHooks.ts，在 CLI 初始化时注册。

Hook 事件Matcher作用
PostToolUseRead检测是否读取了会话文件（transcript/memory）
PostToolUseGrep检测是否搜索了会话文件内容
PostToolUseGlob检测是否列出了会话文件
PostToolUseEdit检测是否编辑了 memory 目录中的文件
PostToolUseWrite检测是否写入了 memory 目录中的文件

目的：纯分析用途。每次工具执行后检查访问的文件路径是否属于会话 transcript 或 memory 目录，上报分析事件以统计 memory 系统的使用模式。超时仅 1 秒，不影响正常流程。

5.2 归因追踪 AttributionHooks

动态导入注册（setup.ts 第 355 行），用于跟踪代码建议的来源归属，支持版权/许可合规。

5.3 Post-Sampling 内部 Hooks postSamplingHooks

文件：src/utils/hooks/postSamplingHooks.ts。内部 API，不暴露给 settings.json。在模型采样完成后执行，用于：

  • 技能改进建议
  • Auto-dream（自动梦境生成）
  • Memory 提取

所有错误仅记录日志，永不阻塞执行。

6. 多个 Hook 的决策与异常处理

6.1 配置来源优先级

Hook 配置从多个来源合并，决定哪些 hook 生效：

优先级从高到低： ┌──────────────────────┐ │ 1. policySettings │ ← 管理员远程策略 / MDM，最高优先级 │ (managed-settings)│ allowManagedHooksOnly: true 时，仅此类 hook 运行 └──────────┬───────────┘ ┌──────────┴───────────┐ │ 2. userSettings │ ← ~/.claude/settings.json ├──────────────────────┤ │ 3. projectSettings │ ← .claude/settings.json ├──────────────────────┤ │ 4. localSettings │ ← .claude/settings.local.json ├──────────────────────┤ │ 5. flagSettings │ ← --settings CLI 标志 └──────────┬───────────┘ ┌──────────┴───────────┐ │ 6. pluginHook │ ← ~/.claude/plugins/*/hooks/hooks.json ├──────────────────────┤ │ 7. sessionHook │ ← 内存中的临时 hook（skill frontmatter 等） ├──────────────────────┤ │ 8. builtinHook │ ← 内置 callback（sessionFileAccess 等） └──────────────────────┘

6.2 执行模型：并行而非串行

核心结论：多个 hook 之间不存在先后顺序。所有匹配的 hook 并行执行（Promise.allSettled 语义），各自独立运行。不存在 "先做哪个" 的执行顺序问题。

executeHooks() 流程： getMatchingHooks() ← 收集所有匹配的 hook │ ▼ hookPromises = matchingHooks.map(...) ← 每个 hook 包装为独立的 async generator │ ▼ for await (result of all(hookPromises)) ← 并行执行，逐个收集结果 │ ▼ aggregateResults() ← 合并所有结果，按优先级规则决策

唯一的 "快速路径" 优化：当所有 hook 都是 internal: true 的 callback 时，跳过 span/进度/取消信号，直接顺序批量执行（从 ~6μs 优化到 ~1.8μs）。

6.3 去重机制

多个配置来源可能包含相同的 hook，通过 hook 身份 去重避免重复执行：

Hook 类型身份标识去重行为
command shell + command + if 相同来源上下文内的重复 hook，保留最后一个（new Map() 语义）。不同 plugin/skill 来源的 hook 不会互相去重（key 包含 pluginRoot/skillRoot 命名空间）。
promptprompt + if
agentprompt + if
httpurl + if
callback 不适用 不去重，每个 callback 唯一
function 不适用 不去重，每个 function 唯一

6.4 冲突解决：权限决策优先级

当多个 hook 对同一事件返回不同的权限决策时，采用最保守策略：

权限决策合并优先级（从高到低）： deny > ask > allow > passthrough 示例： - Hook A 返回 allow, Hook B 返回 deny → 最终 deny（最保守） - Hook A 返回 ask, Hook B 返回 allow → 最终 ask - Hook A 返回 allow, Hook B 返回 allow → 最终 allow - 所有 hook 都是 passthrough → 走默认权限流程

注意：Hook 的 allow 不会绕过 settings.json 的 deny/ask 规则。即使 hook 批准了，checkRuleBasedPermissions 仍然运行 —— deny 规则会覆盖 hook 的 allow 决策。

对于其他输出字段（additionalContext、watchPaths、updatedInput 等），多个 hook 的结果是叠加的 —— 每个 hook 产生的附加上下文都会被收集和传递。

6.5 异常处理

Hook 的异常处理通过退出码 + JSON 输出双层协议实现：

结果退出码JSON 输出行为
成功 0 {"continue": true} 或纯文本 正常继续执行
阻塞错误 2 — 停止当前操作，错误反馈给模型。如 PreToolUse 时阻止工具执行
非阻塞错误 ≠0, ≠2 — 仅向用户展示错误信息，不阻塞流程
超时 — — 到达超时时间后发送 AbortSignal，hook 进程被终止
JSON 校验失败 视为 1 格式不合法 非阻塞错误，stderr 包含校验失败详情
异步模式 — {"async": true} Hook 在后台继续运行，结果稍后通过 checkForAsyncHookResponses() 轮询

REPL 内 vs REPL 外执行

存在两套执行路径：

  • executeHooks()（REPL 内）：产生异步生成器消息，暴露给模型作为 system message。用于 PreToolUse、Stop、UserPromptSubmit 等需要影响模型行为的场景。
  • executeHooksOutsideREPL()（REPL 外）：即发即忘式日志，错误仅通过 logForDebugging 记录。用于 Notification、SessionEnd、Worktree 等不需要影响模型行为的场景。

7. Hook 配置写法

7.1 四种 Hook 类型的配置

Command Hook

{
  "type": "command",
  "command": "path/to/check.sh",    // 必填：shell 命令
  "shell": "bash",                   // 可选：bash 或 powershell
  "timeout": 30,                     // 可选：秒
  "statusMessage": "检查中...",      // 可选：自定义进度文字
  "if": "Bash(git *)",               // 可选：权限规则语法过滤器
  "once": true,                      // 可选：执行一次后移除
  "async": true,                     // 可选：后台执行
  "asyncRewake": true                // 可选：后台执行，exit 2 时唤醒模型
}

Prompt Hook

{
  "type": "prompt",
  "prompt": "检查这个命令是否安全: $ARGUMENTS",  // 必填，$ARGUMENTS 为输入占位符
  "model": "claude-sonnet-4-6",                  // 可选，默认 haiku
  "timeout": 30,                                  // 可选：秒，默认 30
  "if": "Bash(git *)",
  "once": true
}

Agent Hook

{
  "type": "agent",
  "prompt": "验证代码变更是否安全: $ARGUMENTS",  // 必填
  "model": "claude-sonnet-4-6",                   // 可选，默认 haiku
  "timeout": 60,                                   // 可选：秒，默认 60
  "if": "Bash(git *)"
}

HTTP Hook

{
  "type": "http",
  "url": "https://api.example.com/hook",   // 必填
  "headers": { "Authorization": "Bearer $API_TOKEN" },  // 可选，支持环境变量插值
  "allowedEnvVars": ["API_TOKEN"],          // 可选：header 中允许的 env var 白名单
  "timeout": 10                             // 可选：秒，默认 600
}

Conclusion

回顾开篇的四个问题：

1. Hook 系统做什么？ 一个生命周期驱动的可编程中间件框架。在 27 个关键节点并行执行 4 种类型的钩子（command/prompt/agent/http），让外部系统介入、审计和增强 Claude Code 的行为。

2. 哪些地方能做 hook？ 27 个事件覆盖完整生命周期 —— 工具执行前后（PreToolUse / PostToolUse / PostToolUseFailure）、会话起止（SessionStart / SessionEnd）、权限决策（PermissionRequest / PermissionDenied）、上下文管理（PreCompact / PostCompact）、子代理（SubagentStart / Stop）、通知、任务、文件监控、工作树管理等。

3. 内置了什么 hook？ 三类：会话文件访问追踪（Read/Grep/Glob/Edit/Write 后检测是否访问了 transcript/memory 文件）、归因追踪（代码建议的版权归属）、Post-sampling 内部 hooks（技能改进、auto-dream、memory 提取）。全部标记为 internal: true，对用户透明。

4. 多个 hook 如何决策？ 并行执行，不存在先后顺序。去重依靠 hook 身份标识（command+shell+if 等），相同来源上下文中重复的 hook 保留最后一个。权限冲突采用 deny > ask > allow > passthrough 的最保守策略，hook 的 allow 不会绕过 settings.json 的 deny 规则。异常通过退出码协议处理（0=成功, 2=阻塞, 其他=非阻塞），超时可精细配置（SessionEnd 仅 1.5s，通用 10min）。
