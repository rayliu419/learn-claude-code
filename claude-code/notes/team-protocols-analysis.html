结构化消息路由框架：九路分流引擎、双端协议处理、忙闲队列策略

一、总览

Claude Code 的协议系统是构建在 Mailbox 文件通信之上的结构化消息路由框架。教学版 s16 提出了 ProtocolEnvelope + RequestRecord + 状态机 三层模型；生产版将其扩展为 useInboxPoller + 12 种协议类型 + 9 路路由 + 模块级回调注册 + 文件锁邮箱的完整体系。

三、Inbox Poller 九路分流引擎

useInboxPoller（src/hooks/useInboxPoller.ts）是协议系统的核心。它是一个 React Hook，每 1 秒 轮询邮箱文件，将未读消息按类型分类路由。

完整路由流程

useInboxPoller() ── 每 1 秒 ── │ ├─ getAgentNameToPoll(appState) ← 过滤 in-process teammate！ │ └─ in-process? → undefined（不走 poller） │ └─ isTeammate? → agentName │ └─ isTeamLead? → leadName │ └─ standalone → undefined │ ├─ readUnreadMessages(agentName, teamName) │ └─ 九路分流 │ ├─ permission_request ──────────────→ Leader 端 │ └─ findToolByName → ToolUseConfirmQueue 入队 │ └─ onAllow → sendPermissionResponseViaMailbox │ └─ onReject → sendPermissionResponseViaMailbox │ └─ 桌面通知 │ ├─ permission_response ─────────────→ Teammate 端 │ └─ hasPermissionCallback? │ └─ processMailboxPermissionResponse │ ├─ approved → onAllow(input, updates) │ └─ rejected → onReject(feedback) │ ├─ sandbox_permission_request ──────→ Leader 端 │ └─ 入 workerSandboxPermissions.queue │ ├─ sandbox_permission_response ────→ Teammate 端 │ └─ processSandboxPermissionResponse │ ├─ shutdown_request ────────────────→ Teammate 端 │ └─ 以普通消息传递（model 自行处理） │ └─ UI 渲染 shutdown 通知 │ ├─ shutdown_approved ───────────────→ Leader 端 │ └─ killPane (tmux) / AbortController (in-process) │ └─ removeTeammateFromTeamFile │ └─ unassignTeammateTasks │ └─ UI 系统消息通知 │ ├─ team_permission_update ──────────→ Teammate 端 │ └─ applyPermissionUpdate('addRules', rules) │ ├─ mode_set_request ────────────────→ Teammate 端 │ └─ 验证 from === 'team-lead' │ └─ applyPermissionUpdate('setMode', mode) │ └─ setMemberMode(config.json) │ ├─ plan_approval_request ───────────→ Leader 端 │ └─ 自动批准（无需用户干预） │ └─ writeToMailbox(teammate, response) │ └─ handlePlanApprovalResponse (in-process) │ └─ 普通消息 ───────────────────────→ 双方 ├─ idle? → 立即提交新 turn └─ busy? → 入 AppState.inbox.messages 队列

忙时/闲时策略

会话空闲时

消息立即通过 onSubmitTeammateMessage() 提交为新 turn。消息格式化为 XML <teammate_message> tag，附带 teammate_id、color、summary 属性。

会话忙碌时

消息排入 AppState.inbox.messages 数组，UI 侧边栏显示待处理通知。当前 turn 结束后，useEffect 检测空闲并交付排队消息。

去重机制

如果 markMessagesAsRead 失败，同一消息会在下轮 poll 中重新读取。Permission 请求通过 toolUseID 去重；普通消息通过 id (randomUUID) 去重。

谁不走 Inbox Poller

In-process teammate 不走 useInboxPoller。原因：in-process teammate 和 Leader 共享 React 上下文和 AppState，使用 poller 会导致消息路由冲突（shared setAppState + AsyncLocalStorage context）。

In-process teammate 使用 waitForNextPromptOrShutdown() 机制：

  1. 优先检查 task.pendingUserMessages[]（Leader 直接 push，零延迟）
  2. 然后轮询文件邮箱（回退机制）
  3. 超时后标记为 idle

四、六大协议详解

4.1 权限协议（Permission Protocol）

这是生产版最核心、教学版完全没有的协议。Worker 的工具调用权限通过 mailbox 转发给 Leader 处理。

Worker Mailbox Leader │ │ │ ├─ 尝试 Bash 分类器 │ │ │ (自动批准) │ │ ├─ createPermissionRequest() │ │ │ ├─ 包含：tool_name, input, │ │ │ │ description, request_id │ │ │ └─ writeToMailbox() ──────────→│ │ │ │ useInboxPoller/1s │ │ ├──────────────────────────────→│ │ │ ├─ ToolUseConfirmQueue │ │ ├─ 用户弹窗 │ │ ├─ 批准/拒绝 │ │ permission_response │ │ ←───────────────────────────────┤ │ processMailboxPermissionResponse │ │ ├─ approved → onAllow(input) │ │ │ └─ rejected → onReject(msg) │ │ │ │ │ │ (用 SwarmPermissionPoller │ │ │ 每 500ms 轮询 resolved 目录 │ │ │ 作为第二层响应通道) │ │

4.2 关闭协议（Shutdown Protocol）

教学版两路协议之一。生产版从 Boolean 响应扩展为完整的四级协商：

Leader Teammate │ │ ├─ InProcessBackend.terminate() │ │ └─ createShutdownRequestMessage │ │ └─ writeToMailbox(inbox) ──────────→│ │ ├─ isShutdownRequest() detect │ ├─ 判断 approve / reject │ ←────────────├─ write shutdown_approved │ └─ shutdown_approved → │ or shutdown_rejected │ ├─ killPane (tmux teammate) │ │ ├─ remove from team file │ └─ approve → exit agent loop + cleanup │ ├─ unassign tasks │ └─ reject → continue working │ └─ UI notification │ │ │ ├─ InProcessBackend.kill() │ │ └─ abortController.abort() ────────→┤ ← 直接 abort，无协商

4.3 计划审批协议（Plan Approval Protocol）

与教学版不同，生产版的 Leader 自动批准 plan_approval_request：

Teammate Leader │ │ ├─ submit plan │ └─ write plan_approval_request ──→│ ├─ isPlanApprovalRequest() detect ├─ 自动批准（无需用户干预） ├─ 继承 permissionMode: │ Leader plan mode? → 'default' │ 否则 → 继承 Leader 当前 mode ├─ writeToMailbox(response) → teammate inbox ├─ handlePlanApprovalResponse(in-process) │ └─ taskState update └─ 同时标记为普通消息 → model 可见 Teammate (useInboxPoller) ├─ 检测到 plan_approval_response ├─ 验证 from === 'team-lead' ← 安全校验 ├─ approved? │ └─ applyPermissionUpdate('setMode', mode) → 退出 plan mode └─ rejected? └─ 记录 feedback [安全设计] 只有 from='team-lead' 的响应被接受， 防止其他 teammate 伪造批准。

4.4 模式设置协议（Mode Set Protocol）

Leader 可以在 TeamsDialog 中更改 teammate 的权限模式：

Leader (TeamsDialog) └─ writeToMailbox(teammate, mode_set_request { mode: 'plan' }) Teammate (useInboxPoller) ├─ 验证 from === 'team-lead' ├─ 解析 mode → permissionModeFromString ├─ applyPermissionUpdate('setMode', mode) ← 本地即时生效 └─ setMemberMode(config.json, mode) ← 持久化到共享配置

4.5 团队权限广播（Team Permission Update）

Leader (UI) └─ writeToMailbox(teammate, team_permission_update { toolName: 'Edit', directoryPath: '/path/to/project', permissionUpdate: { type: 'addRules', rules: [...], behavior: 'allow' } }) Teammate (useInboxPoller) ├─ 验证 permissionUpdate.rules + behavior └─ applyPermissionUpdate('addRules', rules) → 更新 session allow rules，无需用户确认

4.6 空闲通知协议（Idle Notification Protocol）

注册在 teammate 的 Stop hook 中，在每个 turn 结束时触发：

Teammate Stop hook (teammateInit.ts) ├─ setMemberActive(teamName, agentName, false) ← 标记空闲 ├─ createIdleNotification(agentName, { │ idleReason: 'available' | 'interrupted' | 'failed', │ summary: getLastPeerDmSummary(messages), │ completedTaskId, completedStatus, failureReason │ }) └─ writeToMailbox(leadAgentName, notification) Leader └─ 收到 idle_notification → UI 显示队友完成状态

九、总结

协议系统设计哲学："消息统一入邮箱，路由按类型分流，处理看忙闲状态。"

所有结构化协议消息通过同一个文件邮箱通道传输，通过 isStructuredProtocolMessage() 门控过滤后路由到不同的 handler。教学版的"ProtocolEnvelope + RequestRecord + 状态机"三层模型在生产版中被吸收为：消息类型定义 + callback registry 回调 + AppState/文件双重状态跟踪。

关键设计权衡

统一性✅ 所有消息共享同一邮箱通道，架构简单
路由效率⚠️ 每 1s 轮询 + 逐条 try-catch 类型检测，大规模 swarm 可能成为瓶颈
安全性✅ from === 'team-lead' 校验 + Zod schema 反序列化过滤 malformed 消息
实时性⚠️ 文件邮箱 1s 轮询延迟；in-process 通过 bridge 零延迟优化
健壮性✅ 忙时队列 + 去重 + 锁文件 + 双重响应通道（mailbox + disk files）
可扩展性✅ 新增协议类型只需添加 is* 检测函数 + poller 分流分支
