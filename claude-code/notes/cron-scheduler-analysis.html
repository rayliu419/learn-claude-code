三、cron 表达式引擎

解析模型（cron.ts） — 语法树展开方式比教学版更彻底：不匹配当前时间，而是将 5 个字段展开为值集 (number[])。

"*/15 9-17 * * 1-5" → parseCronExpression() → { minute: [0,15,30,45], hour: [9,10,11,12,13,14,15,16,17], dayOfMonth: [1..31], month: [1..12], dayOfWeek: [1,2,3,4,5] }

computeNextCronRun() 从 from 之后开始向前逐分钟推进，支持：

  • 月跳转 (setMonth+1) — 减少大量没必要迭代
  • 日跳转 (setDate+1) — 同样加速
  • OR 语义：dayOfMonth 和 dayOfWeek 都受限制时，任符合即可
  • DST：spring-forward gap 自动跳过，fall-back 重复只触发一次（vixie-cron 兼容）
  • bound：最多 366 天，超限返回 null

cronToHuman() 可读化

"0 * * * *" → "Every hour" "*/5 * * * *" → "Every 5 minutes" "0 9 * * 1" → "Every Monday at 9:00 AM" "0 9 * * 1-5" → "Weekdays at 9:00 AM"

四、抖动（Jitter）系统

这是教学版完全忽视的关键问题："全球用户同时选择 9:00 和 14:30 等整点/半点，产生 API 负载尖峰。" 生产版用两级抖动解决。

1. Recurring Jitter（前向延迟）

对周期性任务，每次计划执行时加一个比例延迟：

公式: delay = taskId_hash × recurringFrac × (interval) 默认: recurringFrac = 0.1, cap = 15min 例: 每小时执行的任务 → 延迟 0~6 分钟 每分钟执行的任务 → 延迟 0~6 秒
  • 比例性：任务周期越长，抖动窗口越大
  • 确定性：从 taskId 的前 8 hex 字符计算，重启后一致
  • 上限保护：recurringCapMs 防止长间隔任务抖动过大

2. One-shot Jitter（后向提前）

对一次性任务（"2:30 提醒我"），在目标时间前最多 90 秒触发：

条件: 分钟字段 % oneShotMinuteMod (默认 30) == 0 即只对 :00 和 :30 产生的任务加抖动 公式: lead = oneShotFloorMs + taskId_hash * (oneShotMaxMs - oneShotFloorMs) 默认: max=90s, floor=0, mod=30 例: "30 14 * * *" → 在 14:29:01 ~ 14:30:00 之间触发 "35 14 * * *" → 无抖动，准点触发（因为 35 % 30 ≠ 0）
  • 只对"人类自然选择的整点/半点"加抖动——这是 API 负载尖峰的真实来源
  • 提前触发而不是延后——因为用户说"2:30 提醒我"，延后就破坏了约定
  • 运维可在事故中调整：设 oneShotMinuteMod=15 覆盖 :00/:15/:30/:45

GrowthBook 运维杠杆

cronJitterConfig.ts 从 GrowthBook 读取 tengu_kairos_cron_config，Zod 验证后注入 getJitterConfig 回调。调度器 check() 每秒重新读取缓存，60 秒自动刷新。无需重启客户端即可调整：

// GrowthBook JSON 配置示例 (tengu_kairos_cron_config) { "recurringFrac": 0.1, // 前向比例 "recurringCapMs": 900000, // 前向上限 (15 min) "oneShotMaxMs": 90000, // 后向最大提前 (90 s) "oneShotFloorMs": 0, // 后向最小提前 "oneShotMinuteMod": 30, // 分钟模门控 "recurringMaxAgeMs": 604800000 // 自动过期 (7 天) }

五、并发安全：Scheduler 锁机制

问题：当多个 Claude Code 实例在同一个项目目录运行（Terminal + IDE + headless），每个实例都会读取 .claude/scheduled_tasks.json 并启动调度器——导致同一个 cron 任务被多次触发。

文件锁: .claude/scheduled_tasks.lock 内容: { sessionId, pid, acquiredAt } 获取流程: 1. O_EXCL ('wx') 原子写 → 成功？ → 我是 Owner 2. 文件存在 → 读锁检查 a. sessionId 是自己的？ → 更新 PID 后返回 true（idempotent re-acquire） b. PID 还活着 (isProcessRunning)？ → 返回 false（被阻止） c. PID 死了（僵锁）？ → unlink + 重试一次 O_EXCL 3. 都不是 Owner → 启动 5s 锁探测定时器 → 每 5s 尝试 tryAcquireSchedulerLock() → 成功时停止探测 Owner 行为: - 只有 Owner 在 check() 中处理文件任务 - 非 Owner 只处理自己的 session-only 任务（内存，无需锁） - 退出时 releaseSchedulerLock() 清理锁文件

设计权衡

方面决策
一致性最终一致性——非 Owner 写入仍在自己的 session 内存中，重启后由 Owner 处理
容错性PID 死亡 → 5s 内锁被其他 session 回收
原子性O_EXCL 系统调用级原子
性能无锁路径 ≈ 内存访问；有锁路径 ≈ 一次文件写

六、任务生命周期

任务数据结构 (CronTask)

type CronTask = { id: string // 8 字符 hex (randomUUID().slice(0,8)) cron: string // 5 字段 cron 表达式 prompt: string // 触发时注入的提示 createdAt: number // 创建时间戳 (epoch ms) lastFiredAt?: number // 上次触发时间戳 (仅 recurring) recurring?: boolean // 是否周期性 permanent?: boolean // 免于自动过期 (仅 assistant 模式) durable?: boolean // 运行时标志: false=session-only agentId?: string // 运行时标志: 归属 teammate }

七、与教学版对比的关键差异

1. 时间模型

教学版生产版
匹配方式每分钟检查"当前时间是否匹配 cron"计算"从锚点到下一次触发之间的毫秒数"
精度控制每秒轮询 + 分钟防重复每秒轮询 + nextFireAt 缓存
时间方向被动判断"现在是不是"主动问"下一次是什么时候"
DST未处理vixie-cron 兼容

生产版为什么用 computeNextCronRun？ 教学版每分钟检查 all tasks against current time，无法处理"session 离线了 2 小时，应该在这期间触发吗"的精确判定。生产版每个任务锚定 createdAt 或 lastFiredAt，支持：首次锚点正确性（30 14 27 2 * → 明年 2 月 27 日，不是明天）；进程重启后从 lastFiredAt 恢复相同的 nextFireAt；缺失检测（从 createdAt 出发，next < now → missed）。

2. 文件 I/O 模型

教学版生产版
读写方式全量 read/writeasync read/modify/write + chokidar 监听
并发无O_EXCL 锁 + sessionId 仲裁
格式[{...}] 数组{tasks:[{...}]} 对象包裹
容错try/except逐条校验，失效任务静默跳过 + debug log
空文件异常处理视为空任务列表

3. 缺失任务的处理

教学版生产版
检测从 lastFired 逐分钟回退，上限 24h从 createdAt 计算 next，next < now → missed
交互返回 missed 列表供调用方处理buildMissedTaskNotification → 指导模型用 AskUserQuestion 询问
安全无特别处理代码 fence 包裹 prompt 防止自注入
范围所有任务仅 one-shot（recurring 由 check() 兜底）

4. 生产者端（工具层）

教学版生产版
参数校验无Zod schema + validateInput 三关（expr 语法 + 可达性 + 数量）
上限无MAX_JOBS = 50
Teammate 限制无teammate 不能创建 durable cron
返回值字符串结构化 {id, humanSchedule, recurring, durable}
容错Invalid → try/exceptinvalid cron → errorCode 分类

九、总结

设计哲学："精确度换可靠性，抖动换算力，锁定换一致性。"

生产版调度器的每一处设计都在三个方面做了权衡。教学版 s14 教会的是"调度器做的是记住未来"，生产版则展示了当"记住未来"扩展到全球用户级时，需要补充并发锁、确定性抖动、可配置运维和 teammate 集成等工程级实现。

关键设计权衡

精确性✅ 不追求毫秒级准时。每秒轮询 + nextFireAt 缓存（Web Worker 级的时钟精度就够了）
API 负载✅ 抖动系统从 cron 语法角度解决全球 API 尖峰，而非在基础设施层做速率限制
多 session✅ O_EXCL 锁 + PID 探针允许 Terminal / IDE / headless 共存而不互相干扰
可运维性✅ 抖动参数由 GrowthBook 推送，不硬编码在 "推荐使用 :07" 的提示词中
可靠性✅ 缺失检测 + AskUserQuestion 交互 + 代码 fence 防自注入 + 孤儿清理
资源管理✅ 一个 setInterval 驱动所有任务，定时器 unref() 不阻止进程退出
