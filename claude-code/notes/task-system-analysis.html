Claude Code 任务系统设计分析

两个任务概念、文件锁并发安全、Swarm 协同编排 — 从教学代码到生产级实现

s12 → src/utils/tasks.ts + src/tasks/ 两个独立子系统 TodoV2 + 运行时 Task Swarm 协同

一、总览

Claude Code 的任务系统并非单一组件，而是两个完全独立的任务子系统共享同一个名称但服务于不同的目的。这是教学代码与生产代码之间最大的概念差异：

核心设计区分："任务"一词在 Claude Code 中同时指代持久化工作图（Work-Graph Task）和运行时执行槽（Runtime Task）。前者是 s12 教学的延续（目标规划 + 依赖关系），后者对应 s13 的后台执行。生产代码中它们是两套独立的代码路径、数据结构、存储机制和生命周期。

二、子系统一：Work-Graph Task（持久任务图）

对应 s12 教学：持久化工作图 + 依赖解析。教学代码以 .tasks/task_N.json 文件 + TaskManager CRUD 展示了最小模型，生产代码在此基础上扩充了并发安全、Swarm 协同、Hook 系统和 UI 集成。

2.1 数据结构

定义于 src/utils/tasks.ts，使用 Zod 做运行时验证：

// TaskSchema（Zod 验证） { id: string, // 递增整数，转为字符串存储 subject: string, // 任务标题 description: string, // 任务描述 activeForm?: string, // 进行时态文案（如 "Running tests"） owner?: string, // 认领 Agent 的 ID status: 'pending' | 'in_progress' | 'completed', blocks: string[], // 该任务阻塞了哪些任务 blockedBy: string[], // 哪些任务阻塞了该任务 metadata?: Record<string, unknown> // 任意元数据 }

2.2 存储布局

~/.claude/tasks/{taskListId}/ .highwatermark ← 最大 ID 标记（防止删除后 ID 复用） .lock ← proper-lockfile 锁文件 1.json ← task.id = "1" 2.json ← task.id = "2" ...

taskListId 的解析优先级（getTaskListId()）：

  1. CLAUDE_CODE_TASK_LIST_ID 环境变量 — 显式指定
  2. Teammate context → 同队成员的 team name（共享任务列表）
  3. getTeamName() — 进程级团队成员
  4. leaderTeamName — 队长创建队伍时设置
  5. getSessionId() — 独立会话

2.3 核心操作：6 个工具

工具功能关键行为

2.4 并发安全：文件锁

生产代码和教学代码最根本的差异之一：生产代码需要处理多个 Claude 进程同时操作任务列表（Swarm 模式）。

三层锁策略

锁范围文件用途
任务列表级.lock创建任务（ID 分配）、claimTask with busy-check、resetTaskList
任务文件级{id}.json更新单个任务、claimTask（无 busy-check）
无锁路径—读操作（getTask, listTasks）：只做原子性文件读取

设计要点：锁的粒度和作用域精确匹配操作语义。claimTaskWithBusyCheck 需要读所有任务来判断 agent 是否繁忙，因此使用列表级锁；简单的状态更新只需要任务文件级锁。锁超时使用 proper-lockfile 的 retry 选项（30 次 × 逐步退避），避免即时失败。

2.5 依赖关系：双向维护

blockTask(fromTaskId, toTaskId) 是依赖管理的核心函数：

A 阻塞 B（A→B）： 1. A.blocks 中加入 B 的 ID 2. B.blockedBy 中加入 A 的 ID → 完成 A 后 B 自动解除阻塞 → B 的 is_ready = pending && blockedBy 为空

TaskList 工具返回的 blockedBy 会智能过滤已完成的阻塞任务——模型看到的 blockedBy 永远是"仍然需要等待的任务"。

2.6 Hook 系统集成

两个 Hook 事件：TaskCreated 和 TaskCompleted。执行方式与所有其他工具 Hook 一致：

  • Hook 可以返回阻塞错误（exit code 2），此时任务创建/完成被回滚
  • TaskCreate 阻塞 → 自动 deleteTask() 回滚
  • TaskUpdate 完成阻塞 → 返回 error 但不回滚已有改动

2.7 UI 自动隐藏

TasksV2Store — 单例 React Store
├─ 所有任务完成 → 启动 5s 定时器
├─ 5s 后验证仍全部完成 → resetTaskList() 清空
├─ 有新未完成任务 → 取消定时器
└─ 隐藏后 → 自动折叠 expandedView 为 'none'

设计意图：完成任务后 5s 清空，保持 UI 整洁。同时用户完成任务时有足够时间看到完成状态。

三、子系统二：Runtime Task（运行时执行槽）

对应 s13 教学：后台命令执行 + 通知队列。生产代码中这比 s12 的 Work-Graph Task 早了约一年出现——最初只有 Bash 执行，后来逐步演化为多类型执行框架。

每个 Runtime Task 创建时自动分配输出文件：

stopTask(taskId, { getAppState, setAppState }): 1. 查找任务 → 检查 status === 'running' 2. getTaskByType(type) → 获取 kill 实现 3. taskImpl.kill(taskId, setAppState) 4. bash 任务静默抑制 exit 137 通知 5. 发送 SDK 终止事件 (emitTaskTerminatedSdk)

五、Swarm 模式下的任务协同

Swarm 模式是驱动 Task 系统复杂性的核心场景。没有 Swarm，任务系统可以保持内存文件读写；Swarm 引入了文件锁、claim 协议、mailbox 通知、agent 繁忙检查等一系列复杂性。

5.1 任务即编排契约

在 Swarm 模式下，Work-Graph Task 成为多 agent 协同的核心数据结构：

队长 (Team Leader) ├─ 创建任务 → TaskList 被设置为团队名称 ├─ 分配任务 → TaskUpdate 设置 owner ├─ 通过 mailbox 通知具体 teammate └─ 监控各 agent 状态 队友 (Teammate) ├─ 完成任务 → TaskList 查找下一项可用任务 ├─ 认领 (claimTask) → 原子性地检查 + 分配 owner └─ 被阻塞 → 通知队长 任务列表文件锁 └─ 多个 Claude 进程同时操作同一任务列表 └─ proper-lockfile 防止冲突

5.2 原子认领协议

claimTask(taskListId, taskId, agentId, opts?)
├─ 简单路径（默认）:
├─ 锁定任务文件
├─ 检查: not_found? → 失败
├─ 检查: 已被他人认领? → already_claimed
├─ 检查: 已完成? → already_resolved
├─ 检查: 未解析的 blocker? → blocked
└─ 设置 owner → 成功
└─ busy-check 路径 (opts.checkAgentBusy = true):
├─ 锁定整个任务列表
├─ 读所有任务 → 原子性判断 agent 是否已持有多条开放任务
├─ 已有开放任务 → agent_busy (含 busyWithTasks 列表)
└─ 空闲 → 认领

这种双层协议确保了"一个 agent 一次只做一件事"的语义，且避免 TOCTOU 竞争条件。

5.3 队友离开时的清理

unassignTeammateTasks() 处理队友被杀死或正常关闭的场景：

teammate 终止/关闭 ├─ 遍历所有开放任务，owner == teammate 的 ├─ updateTask: owner → undefined, status → pending ├─ 汇总被释放的任务列表 └─ 通知队长: "X was terminated/shut down. N task(s) unassigned"

5.4 自动任务看门狗

useTaskListWatcher Hook 使任务列表模式可以完全自动化：

useTaskListWatcher(props)
├─ fs.watch 监听任务目录变更（1s debounce）
├─ 不处于加载状态时检查可用任务
├─ findAvailableTask: pending + 无 owner + blocker 已全部完成
├─ claimTask 原子认领
└─ formatTaskAsPrompt → 提交给主循环
└─ 提交失败 → 释放认领

这个 Hook 使得 Claude 可以像一个 CI worker 一样持续从任务队列拉取任务执行，无需手动触发。

六、历史演变：TodoWrite → TodoV2

任务系统经历了从 TodoWrite 到 TaskCreate/TaskList/TaskGet/TaskUpdate 的重构（V2 化）：

维度TodoWrite（传统）TodoV2 / Task Tools
数据结构AppState 内的内存数组磁盘 JSON 文件
持久性不跨会话跨会话（~/.claude/tasks/）
依赖管理无blocks / blockedBy 双向图
并发安全无（单进程）proper-lockfile 文件锁
Swarm 支持无claimTask + mailbox + agent 状态查询
Hook无TaskCreated / TaskCompleted
元数据无metadata map + activeForm

重要的设计迁移细节

状态名迁移：早期版本使用 open/resolved 等状态名。getTask() 中有一个兼容性迁移逻辑，将 ant 用户旧数据中的 open → pending，resolved → completed，planning/implementing/reviewing/verifying → in_progress。

九、总结

设计哲学："任务系统是两类完全不同的事物的统一名称。"

生产 Claude Code 中的"任务"一词同时承载了计划编排（Work-Graph Task）和运行时执行（Runtime Task）两个概念。教学代码的 s12 和 s13 分别对应这两个子系统，但教学代码中两者独立、互不干扰；而生产代码中两者共享了"task"这个术语，却在数据结构、存储位置、生命周期、并发模型上完全不同。理解这个区分是理解 Claude Code 任务架构的关键。

关键设计权衡

并发安全✅ 三层锁策略（列表级/文件级/无锁）覆盖不同操作。proper-lockfile 30 次重试容忍 ~10 进程同时操作
可扩展性✅ Runtime Task 的 7 种类型插件化注册。新增一种 task 只需实现 { name, type, kill } 接口并注册
命名混淆⚠️ "Task"同时指两个完全不同的概念。Work-Graph 任务和 Runtime 任务的数据结构、生命周期、代码位置完全不同，但共享同一个词汇。新读者几乎必然混淆
持久化策略✅ Work-Graph 任务全量磁盘持久（JSON 文件），跨会话存活。Runtime 任务状态在内存，输出文件在临时目录，进程结束后可清理
Swarm 协同✅ 任务即编排契约：claimTask + mailbox + agent 状态查询 + busy-check 构成完整的多 agent 协同协议
Hook 集成✅ TaskCreated/TaskCompleted 阻塞 hook 让外部脚本可以控制任务生命周期——例如 CI/CD 闸门
UI 设计✅ 5s 自动隐藏 + useSyncExternalStore 单一订阅源 + fs.watch 文件级监听——全站只有一个文件 watcher

从教学代码到生产的演进启示

  1. Task 命名在大型系统中需要更精确。教学代码的 s12 "任务" 和 s13 "后台任务" 清楚地区分了"工作目标"和"执行槽"。生产代码中二者都叫 "task"，但代码路径完全不同。如果重来一次，"work-item" 和 "execution-slot" 的命名区分会更清晰
  2. 并发安全是教学到生产的最大鸿沟。s12 的教学代码假设单进程单用户。生产代码中 Swarm 模式需要文件锁、原子认领、TOCTOU 防护——增加了约 70% 的代码复杂度
  3. Hook 系统使任务可编程。TaskCreated/TaskCompleted hooks 让任务系统成为更大的自动化流程的一部分，而不仅仅是模型内部的计划工具
  4. 不要低估 UI 集成的复杂度。任务工具的提示词、useSyncExternalStore 的 React 集成、5s 隐藏逻辑、fallback 轮询——UI 部分的代码量和业务逻辑层几乎相当
  5. 状态迁移需要向后兼容。从 open→pending、resolved→completed 的迁移代码表明，生产系统中数据结构演化比教学代码复杂得多
