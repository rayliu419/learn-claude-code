Claude Code 错误恢复系统设计分析

三路恢复、主动预防与死亡螺旋防护 — 从教学代码到生产级实现

s11 → query.ts, withRetry.ts, autoCompact.ts 5 种恢复策略 + 2 种预防机制 ~1729 行主循环

一、总览

Claude Code 的错误恢复系统远不止 s11 教学的三种路径。生产代码构建了一套分层恢复 + 主动预防 + 防护网的完整体系：

核心设计思路：不把所有恢复逻辑塞在一个地方。按错误的性质分派给不同的子系统——API 层的重试由 withRetry 处理，上下文过长由 compact 家族处理，输出截断由主循环状态机处理。每个子系统独立演化，通过 query loop 的 State 状态机串联。

关键数字

恢复策略数5 种（max_tokens 升级 + 恢复消息 / collapse drain / reactive compact / auto compact / API retry）
预防机制2 种（token 阈值预警 + 硬阻断）
max_output_tokens 重试上限3 次（MAX_OUTPUT_TOKENS_RECOVERY_LIMIT）
auto compact 连续失败断路器3 次（MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES）
API retry 上限10 次（DEFAULT_MAX_RETRIES）
529 退避上限3 次 → Opus→Sonnet 降级 or fallback
compact summary 保留 token20,000（MAX_OUTPUT_TOKENS_FOR_SUMMARY）
base backoff delay500ms（BASE_DELAY_MS）
错误分类种类20+（timeout, rate_limit, auth, pdf, image, tool_use...）

三、五条恢复路径详解

路径 1：max_output_tokens 恢复 s11 策略 1 增强版

对应 s11 的"输出截断后发送 continuation"。但生产版本多了静默扩容步骤。

执行顺序

流式 API 返回 max_output_tokens │ ├─ isWithheldMaxOutputTokens() = true → withhold，不 yield 给用户 │ 错误被压制，等 recovery │ ├─ Step 1: 静默扩容 (8k → 64k) │ 条件: 门控 tengu_otk_slot_v1 开启 && 未设置 maxOutputTokensOverride │ 操作: 重新发送完全相同请求 (max_tokens: 64000) │ 标记: transition = max_output_tokens_escalate │ ├─ Step 2: Continuation 消息 │ 条件: maxOutputTokensRecoveryCount < MAX_OUTPUT_TOKENS_RECOVERY_LIMIT (3) │ 操作: 注入 "Output token limit hit. Resume directly — no apology..." │ 标记: transition = max_output_tokens_recovery │ └─ 恢复耗尽: 把 withheld 的错误 yield 给用户

关键代码：query.ts:1185-1256

路径 2：Prompt-too-long 恢复 三层递进

s11 只有一个 auto_compact() 做 LLM 摘要。生产版本有三层恢复、逐层尝试：

层 1：Context Collapse Drain 最轻量

门控 CONTEXT_COLLAPSE。contextCollapse.recoverFromOverflow() 从"折叠队列"中弹出已标记为可折叠的上下文组。

  • 按组折叠，保留 granular 上下文（不像 summarize 那样损失细节）
  • 只执行一次：如果本次循环已经是 collapse_drain_retry，跳过进入层 2
  • 返回 committed > 0 时继续循环

层 2：Reactive Compact 中等开销

门控 REACTIVE_COMPACT。在收到 API 的 413/PTL 错误后被动触发。

  • 解析 errorDetails 获取 actual/limit 差值 → getPromptTooLongTokenGap()
  • 利用差值跳过多个组，不必逐组剥离
  • 也会处理 media size 错误（图片/PDF 超限 → stripImagesFromMessages）
  • 设置 hasAttemptedReactiveCompact = true 防止二次触发

层 3：Auto Compact 主动预防

在每个 query 循环开始前主动检查 token 阈值。

  • 阈值 = contextWindow - 13000 (AUTOCOMPACT_BUFFER_TOKENS)
  • 连续失败 3 次触发断路器（MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES）
  • 预留 20000 tokens 给 summary 输出

路径 3：API 错误重试 s11 策略 3 增强版

s11 只是简单的 exponential backoff。生产版本有细粒度错误分类和特定处理。

withRetry.ts 核心设计

API 调用 │ ├─ 429 (rate limit) │ ├─ fast mode active → 检查 retry-after │ │ ├─ < 阈值 → 等待后重试 (fast mode 保留) │ │ └─ ≥ 阈值 → cooldown (切换到标准速度模型) │ └─ 新 API 头部 → 统一限速消息 + overage 检查 │ ├─ 529 (overloaded) │ ├─ 前台源 (用户等待) → 重试 │ ├─ 后台源 → 立即放弃 (避免容量级联) │ └─ Opus 连续 3 次 529 → FallbackTriggeredError (→ Sonnet 降级) │ ├─ 401/403 (auth) │ ├─ OAuth token 过期 → handleOAuth401Error → 刷新 → retry │ └─ API key 无效 → CannotRetryError → 用户登录 │ ├─ ConnectionError │ ├─ Timeout → 分类为 api_timeout │ ├─ ECONNRESET/EPIPE → disableKeepAlive → retry │ └─ SSL 错误 → 分类为 ssl_cert_error │ ├─ Max_tokens context overflow │ ├─ 解析实际/限制 token 数 │ ├─ 调整 max_tokens = availableContext - 1000 safety buffer │ └─ 确保 ≥ FLOOR_OUTPUT_TOKENS (3000) │ └─ 400 (tool_use/tool_result mismatch) ├─ 记录详细日志 (tengu_tool_use_tool_result_mismatch_error) └─ 提示用户 /rewind 恢复

路径 4：阻断 & 预警 预防性

在 API 调用前就阻止无法处理的上下文：

层级条件行为例外
预警 (Warning)token > warningThresholdUI 显示黄色警告—
错误 (Error)token > errorThresholdUI 显示红色警告—
auto-compact 阈值token > autoCompactThreshold自动触发 LLM compaction断路器 3 consecutive failures 后停用
硬阻断 (Blocking)token > blockingLimit返回 blocking_limit 错误跳过条件: 刚 compact 完 / 是 compact 子 Agent / collapse 门控开启

阈值计算：autoCompactThreshold = contextWindow - 13000；buffer 常量可配置

路径 5：工具执行错误 静默恢复

工具执行失败不中断主循环。每个工具调用的结果是包装在 tool_result 中的文本消息——LLM 自主决定如何处理：

runTools()
└─ 每个工具尝试 `handler(...)`
├─ 成功 → 把输出作为 tool_result 返回给 LLM
└─ 失败 → `"Error: {e}"` 作为 tool_result 返回给 LLM
    LLM 看到错误后自行决定重试或换方案

某些工具的主动恢复：

BashTool沙箱超限 → 提示使用 dangerouslyDisableSandbox:true 重试
FileReadTool文件超限 → 建议用 offset/limit 分段读取
AgentTool子 Agent 错误 → 在 tool_result 中传递错误文本

四、死亡螺旋防护机制

生产代码中最重要的设计之一：防止错误恢复本身产生更多错误，导致无限循环。

1. Reactive Compact 仅尝试一次

问题：Layer 2 (LLM summarize) 消耗 token。如果 summarize 后上下文仍然太长，再次触发 PTL → 再次 summarize → 无限消耗。

方案：hasAttemptedReactiveCompact flag。首次触发后设为 true，下次循环不再触发。恢复耗尽后直接 surface 错误。

2. Auto Compact 断路器

问题：auto compact 本身调用 API。如果 compact consistently 失败（每轮都失败），无限重试会浪费大量 API 调用（BQ 显示最多 3,272 次连续失败）。

方案：MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3。连续失败 3 次后停用 auto compact，不再重试。

3. Stop Hooks 不在 API 错误后运行

问题：LLM 从未产生有效回复，stop hooks 评估空消息产生 blocking error → 触发重试 → 触发了相同的 PTL → 无限循环。

方案：

  • API 错误消息 → executeStopFailureHooks() 只记录，不触发 blocking
  • Stop hook blocking 错误迭代中 hasAttemptedReactiveCompact 不被重置

4. 529 后台源不重试

方案：只有用户正在等待的查询源（repl_main_thread, sdk, hook_agent 等）才重试 529。后台源（摘要、标题、建议、分类器）立即放弃——在容量级联中每个重试都是 3-10× 网关放大，而且用户看不到这些失败。

5. Death Spiral 感知的 Collapse Drain

collapse drain 只试一次：如果本次已经是 collapse_drain_retry 状态，跳过 collapse drain，直接跳到 reactive compact。防止"折叠→仍然超长→再折叠→..."。

错误消息构造原则

  • 面向交互式 vs 非交互式：大多数消息通过 getIsNonInteractiveSession() 分支，CLI 用户得到 "Double press esc" 提示，SDK/自动化用户得到无交互建议的纯文本
  • 敏感信息不泄露：错误消息不包含 API key、模型 ID、token 数量等敏感信息（但 errorDetails 给 recovery 路径解析用）
  • 可操作：每个错误提示都包含具体操作（"/login"、"/model"、"/rewind"、"esc esc"、"/compact"）

八、代码关键设计模式

1. 状态机驱动的恢复

主循环用 State 类型追踪恢复状态：

type State = { messages: Message[] autoCompactTracking: AutoCompactTrackingState maxOutputTokensRecoveryCount: number // max_tokens 连续恢复次数 hasAttemptedReactiveCompact: boolean // 防止 reactive compact 无限循环 maxOutputTokensOverride: number // 8k→64k 升级 stopHookActive: boolean // 防止 stop hook 循环 transition: Continue | undefined // 恢复原因（用于测试断言） }

2. Withhold + Recovery 分离

恢复性错误在流式传输时被"扣留"（withhold），不 yield 给消费者，等到 recovery 尝试后再决定是否显示：

API 流式事件 │ └─ 是恢复性错误？ (PTL / media / max_output_tokens) │ ├─ Yes → withhold (不 yield) │ ↓ 加入 assistantMessages │ ↓ 流结束后尝试 recovery │ │ │ ├─ recovery 成功 → 不 yield 错误，继续循环 │ └─ recovery 耗尽 → yield 错误给用户 │ └─ No → yield 给 SDK 消费者

3. 可测试性设计

State.transition 字段让测试可以断言哪个恢复路径触发了，而不必检查消息内容：

transition: undefined → 首次循环 transition: collapse_drain_retry → Context Collapse 触发了 transition: reactive_compact_retry → Reactive Compact 触发了 transition: max_output_tokens_escalate → 8k→64k 升级 transition: max_output_tokens_recovery → Continuation 消息 transition: stop_hook_blocking → Stop hook 阻止 transition: token_budget_continuation → +500k 继续

4. 门控 Feature Flag

高级恢复路径（reactive compact、context collapse、micro compact）通过 feature() 门控条件导入，非门控构建中对应的代码树摇删除：

const reactiveCompact = feature('REACTIVE_COMPACT') ? (require('./services/compact/reactiveCompact.js') as ...) : null

十一、总结

设计哲学："分层恢复，每层只做一件事。每层有自己的防护网。"

教学代码的三路恢复在生产中变成了五路恢复 + token 预警 + 死亡螺旋防护。每个恢复路径都仔细考虑了两个方向——"如何恢复"和"恢复耗尽时如何安全退出"。

关键设计权衡

鲁棒性✅ 多层恢复保证了极高的自愈能力。collapse drain 最轻量，reactive compact 兜底，auto compact 预防
成本控制⚠️ LLM-based recovery（auto compact, reactive compact）消耗 API。断路器/Counter 防止失控浪费。BQ 数据显示 3,272 次连续失败用户因此被保护
用户体验✅ Withhold 机制让用户在 recovery 成功时完全看不到错误。失败时给出可操作的具体提示（/login、/model、/rewind）
复杂性⚠️ 状态机的 7+ 种 transition、门控条件导入、两个独立子系统（collapse 和 reactive compact）的 withhold/recovery 协调—测试覆盖是关键
可测试性✅ State.transition 让测试断言 recovery 路径；bun:bundle 的 feature() 门控使单元测试可 mock 路径
错误可观察性✅ classifyAPIError() 产生标准化标签 → Datadog 监控；tengu_ prefix events 用于 Statsig 链路跟踪

从教学代码到生产的演进启示

  1. 先预防，后恢复。最有效的恢复是不需要恢复。s11 没有预防机制，生产代码有完整的 token 阈值预警 + 主动 compact
  2. 每层恢复要有退路。s11 的无限重试可能导致浪费。生产代码每层都有 Counter 或 Flag 防止无限循环
  3. Feature Flag 管理成熟度。高级恢复路径以门控条件导入，既支持渐进式发布，又让非门控构建自动排除死代码
  4. 用户看到的错误要可操作。s11 朴素地打印错误信息。生产代码为每个错误类型提供具体的用户操作路径
  5. 测试必须能验证恢复路径。State.transition 枚举的设计让测试能够断言 "collapse drain 触发了" 而不是检查消息文本
