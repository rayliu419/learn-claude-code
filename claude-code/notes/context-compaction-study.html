一、Summary —— 设计哲学与核心直觉

Context compaction 解决的是一个简单但残酷的问题：LLM 的上下文窗口是物理上限。模型只能"看到"有限的信息。用户希望一个会话可以无限持续，但 token 预算就是那么多。压缩机制就是在这两个矛盾之间做缓冲。

核心直觉：不要总用最贵的手段。

想象整理一个堆满文件的桌面。你不会每次觉得乱就把所有文件扔进碎纸机（LLM 总结），而是：

  • 先把明显没用的草稿纸扔掉（规则驱动裁剪）
  • 把还在用的文件叠整齐（缓存编辑）
  • 看一眼自己的笔记本来回忆上周做了什么（会话记忆复用）
  • 最后，以上都不够，才把旧文件归档成一份摘要（LLM 压缩）

这就是 Compaction 系统的架构哲学：层层递进，轻量优先，让后续层可能不需要触发。每一层都是一个独立的安全网，成本递增但能力也递增。上层失败了，下层兜住。

另外一个关键直觉：不要等出事了再解决。系统在每次 API 调用前都做一次 token 用量检查，在接近阈值之前就主动行动。这不是事后补救，而是预防性维护。

二、全局景观：五大战场

Context Compaction 不是在单一层面解决问题。系统在五个不同的战场上同时作战，每个战场有自己的武器和策略：

战场策略代价谁执行
删除 不总结，直接扔掉不需要的历史 零（数组操作） Snip
绕路 通过轻量操作避免触发压缩 几乎为零 Tool Budget、Microcompact、Context Collapse
裁剪 用规则驱动丢弃旧工具结果 零 LLM 调用 Tool Result Budget（截断超大结果）、Time-based Microcompact（清除旧工具结果）、Cached Microcompact（缓存编辑）
复用 使用已有的会话笔记代替摘要 零 LLM 调用但依赖后台任务 Session Memory Compact
总结 让 LLM 生成摘要浓缩历史 一次 LLM API 调用（~200K tokens） Full Compact (Forked Agent + Cache Sharing)

这个分层的核心价值：大多数情况下，最贵的路径（Full Compact）根本不需要执行。前四层（删除 + 绕路 + 裁剪 + 复用）覆盖了绝大多数场景，只有它们都搞不定时才走到 LLM 总结。

如果所有预防措施都失败，API 返回了 413（prompt too long）错误，系统还有最后一层反应式压缩作为兜底。

每次 API 调用前的检查链条： ① getMessagesAfterCompactBoundary — 从最后一次压缩边界开始切片 ② Snip → 过滤/删除已标记为 snipped 的消息 ③ Tool Budget → 截断超大工具结果 ④ Microcompact → 清除旧工具结果（时间触发或缓存编辑） ⑤ Context Collapse → 投影式折叠（可选，与 autocompact 互斥） ⑥ Autocompact → 阈值触发，尝试压缩 ├─ Session Memory Compact（零 LLM 调用，优先） └─ Full Compact（Forked Agent + LLM 总结） ⑦ API 调用 → 如果返回 413 ├─ Context Collapse Drain └─ Reactive Compact（反应式压缩）

三、Snip —— 直接删除，不总结

Snip 是压缩链条中成本最低的第一层：不调用 LLM、不生成摘要、不产生任何 API 费用。它就是纯数组操作——在每次 API 调用前，把模型不需要看到的低价值整轮对话从消息数组中直接过滤掉。

滤掉三类低价值消息：

  • 空结果 —— 比如 grep 没找到匹配、Read 一个不存在的文件、Glob 返回空列表
  • 被用户拒绝的工具调用 —— 模型提议运行了某个操作，用户点了拒绝
  • 已被之前压缩覆盖的旧轮次 —— 已经总结过的对话，不需要再保留原始消息

系统还提供了一个 SnipTool，让模型可以在对话中主动要求删除特定消息。每条 user 消息末尾被自动附加了 [id:abc123] 短 ID 标签，模型可以引用这些 ID 来请求删除。

因为 Snip 是每个 API 调用前最先跑的步骤，如果它释放的 token 足够多，让总用量降到阈值以下，后面的所有步骤（Microcompact、AutoCompact 等更昂贵的操作）就根本不需要执行。

四、绕路：如何避免触发压缩

最好的压缩是不压缩。系统有多个轻量机制在 autocompact 决策之前运行，如果它们释放的 token 足够让用量降到阈值以下，autocompact 就不会触发。这就像"先扫地再看要不要大扫除"。

Tool Result Budget —— 截断超大结果

如果某个工具返回了特别大的结果（例如读取一个巨型文件），将其内容替换为截断版本。只修内容，不碰缓存结构。在 microcompact 之前运行。

Microcompact —— 两条互斥路径

时间触发路径：如果距离上一条 assistant 消息超过 60 分钟，说明服务器侧的 prompt cache 已经过期了——无论内容是否修改，下次请求都会重写整个 prefix。那就提前把旧工具结果的内容清除，替换为 [Old tool result content cleared]，这样重写时体积更小。只保留最近 5 个工具的结果，其余全部清除。

缓存编辑路径：利用 Anthropic API 的 cache_edits 功能，在不破坏 prompt cache 的前提下删除旧的工具结果。这是更精细的操作——不修改本地消息内容，而是生成一批 cache_edits 块附加到下一次 API 请求中。通过维护模块级的注册状态来追踪哪些工具结果可以被安全删除。

两条路径的关系：时间触发和缓存编辑是互斥的。时间触发意味着 cache 已经冷了，用传统的 cache_edits 没有意义。缓存编辑路径只在 cache 还是热的（即用户持续活跃）时才跑。

Context Collapse —— 投影式折叠（替代方案）

这是一个与 autocompact 互斥的实验性功能。当启用时，系统使用"投影"而不是"压缩"来管理上下文。折叠操作不修改 REPL 的完整历史，而是在读取时投影出折叠后的视图。~90% token 用量时开始提交折叠，~95% 时阻塞等待折叠完成。

为什么与 autocompact 互斥？Autocompact 在 ~93% 触发，恰好在 collapse 的提交阈值（90%）和阻塞阈值（95%）之间。两者同时启用，autocompact 会在 collapse 来得及保存细粒度上下文之前用一个大摘要覆盖所有内容。

五、裁剪：规则驱动的丢弃

当需要压缩时，首先要决定的是"丢弃什么"。这个决策本质上是规则驱动的，而不是交给 LLM 判断。LLM 只负责"如何浓缩"，不负责"丢弃哪些"。这是非常重要的设计选择：规则是可预测、可测试、零成本的；LLM 的决策则不可预测且昂贵。

规则的核心是几个简单的约束：

  • 最少保留 10K tokens：压缩后不能把上下文压得太干
  • 最多保留 40K tokens：压缩后也不能留得太多
  • 最少保留 5 条文本消息：保证有足够的人类对话上下文
  • 工具配对完整性：不能拆散 tool_use 和 tool_result 的配对
  • 共享 message.id 的保护：流式产生的分片消息（thinking block + tool_use）要一起保留
  • 压缩边界（compact boundary）是地板：不会向前跨越之前的压缩边界，防止磁盘不连续性

规则从 lastSummarizedMessageId 之后开始计算，向后扩展直到满足所有约束。这个算法没有 API 调用，纯粹是数组操作和 token 估算。

工具配对修复案例：有一个索引 N+1 的 assistant 消息包含 tool_use: ORPHAN_ID，而 N+3 的 user 消息包含 tool_result: ORPHAN_ID。如果压缩从 N+2 开始截断，ORPHAN_ID 的 tool_result 就没有对应的 tool_use 了，API 会报错。调整算法会识别到这个情况，自动把起始索引回退到 N+1。

压缩后还有一套附件重建规则：

  • 最多恢复 5 个最近读取的文件，总预算 50K tokens，单文件上限 5K
  • 最近调用的 skills 重新注入，单 skill 上限 5K，总预算 25K
  • Plan 文件、后台 agent 状态等也会被重新注入

六、复用：零 LLM 调用的会话笔记

这是系统中最优雅的优化。Claude Code 有一个后台任务在持续提取会话笔记（session memory）——不断从历史对话中提取关键信息。当需要压缩时，优先使用这些已经提取好的笔记来构建摘要，而不是调用 LLM 去重新阅读整个对话。

为什么不需要调用 LLM？ 因为摘要内容已经在 session memory 里了。系统只需要做三件事：

  1. 找到最后被摘要的消息 ID（lastSummarizedMessageId）
  2. 用规则算法（上面说的 token 阈值 + 配对保护）决定保留哪些最新消息
  3. 把 session memory 内容 + 保留的最新消息拼接成一个有效的消息数组

整个过程零 LLM 调用。只有当 session memory 为空（新会话或后台任务还没完成提取），或者压缩后的内容仍然超过阈值时，才回退到昂贵的 Full Compact。

两种场景：正常对话有 lastSummarizedMessageId，只保留该 ID 之后的消息。Resumed session（恢复的会话）没有 lastSummarizedMessageId，但有 session memory 内容——保留所有消息，但使用 session memory 作为摘要来源，相当于对已有内容做了"标记来源"而不是"重新提取"。

七、总结：LLM 驱动的浓缩

当 Session Memory Compact 不可用或不足以让 token 用量降到阈值以下时，系统调用 Full Compact。这是最昂贵但最彻底的路径。

Forked Agent + Cache Sharing

Full Compact 使用一个 forked agent（子进程）来调用 LLM 生成摘要。这个子进程共享主对话的 prompt cache——相同的 system prompt、tools 和 messages prefix。这意味着 compact API 调用的 cache 命中率高达 ~98%。如果没有 cache sharing，每次 compact 将产生 ~200K token 的 cache creation 成本。

预处理

在发送给 LLM 总结之前，消息数组经过两道预处理：

  • stripImagesFromMessages：图片和文档替换为 [image] / [document] 文本标记。防止图片撑爆 compact API 自身的 token 窗口
  • stripReinjectedAttachments：去掉压缩后会重新注入的 skill_discovery / skill_listing 等附件类型

九维度总结

LLM 被要求按 9 个维度总结对话：用户意图、技术概念、文件与代码、错误与修复、问题解决进展、所有用户消息（非工具结果）、待处理任务、当前工作状态、可选的下一步。模型先输出 <analysis> 草稿块再输出 <summary>，系统剥离 analysis 块只保留 summary 放入后续上下文——analysis 是给模型的"草稿纸"，自身不占用上下文。

PTL 重试

如果 compact API 调用本身也 Prompt Too Long（要总结的消息太多），系统按 API round 分组消息，从最老的一组开始丢弃，最多重试 3 次。如果无法解析 token 缺口（某些 Vertex/Bedrock 错误格式），退而丢弃 20% 的组。

摘要的自我意识

压缩后注入的 summary 消息包含精确的自我认知指令：

  • "This session is being continued from a previous conversation that ran out of context."
  • Transcript 文件路径（模型需要时可以读取完整历史）
  • Autocompact 模式："Resume directly — do not acknowledge the summary"
  • Proactive mode 特殊提示：这不是第一次 wake-up

八、兜底：当所有防线都失效

当所有前置压缩都未能阻止 API 返回 413（prompt too long）错误时，系统进入反应式压缩（Reactive Compact）流程：

  1. 错误暂扣：413 错误在 streaming loop 中被 withhold，不立即显示给用户
  2. Context Collapse Drain：如果 Context Collapse 启用，排空所有 staged 折叠队列
  3. 生成紧凑摘要：调用 LLM 生成更紧凑的摘要并丢弃超出部分
  4. 媒体错误处理：如果原因是图片/PDF 太大，通过 stripImages 后重试
  5. 全部失败：才向用户显示 "Prompt is too long" 错误

关键设计决定：不触发 stop hooks。因为 hook 可能会注入更多 token，导致 413 → hook → 更多 token → 413 的死循环。

当 token 用量达到 effectiveWindow - 3K 且所有恢复手段都失败后，系统阻止继续对话，用户必须手动 /compact 或开启新 session。这是最终拦阻。

九、自我保护：电路断路器

最有趣的设计之一是电路断路器。数据表明：1,279 个 session 曾连续 50+ 次 autocompact 失败（最多 3,272 次），每天浪费约 25 万次 API 调用。

解决方案：连续 3 次 autocompact 失败后，停止重试。断路器跳闸后，即使 token 用量超过阈值也不再触发。这避免了在"压缩本身不可行"的情况下（例如上下文已经不可恢复地超过限制），系统陷入无限重试的泥潭。

断路器状态是每个会话级别的：重置在成功时发生，失败计数在每次失败后递增。这是个明智的工程取舍——与其尝试不可能的任务，不如让用户介入手动处理。

十、Conclusion —— 几条关键设计原则

1. 代价分层是核心架构

不是单一算法，而是分层系统。从零成本的 Snip 到昂贵的 Full Compact，每一层都是上一层安全网。设计目标不是"完美的压缩"，而是"压缩成本恰好够用"。如果 Snip 释放了足够 token，那么 Microcompact 和后面的所有层都变成 no-op。

2. 规则决策优先，LLM 决策兜底

"丢弃什么"由规则决定——阈值、区间、配对完整性，全部可预测、可测试、零成本。LLM 只做它擅长的事："如何浓缩"。即使是 Full Compact，参数（保留多少、保留哪些文件、保留哪些 skill）也是规则设定的。

3. 缓存效率是隐藏主线

很多设计决策围绕 prompt cache 展开。Cache-sharing 的 forked agent 让 compact 的 ~200K token 几乎全部 cache-hit。时间触发的 microcompact 判断 cache 已冷才出手。缓存编辑路径则在不破坏热 cache 的前提下清理旧内容。一台 API 请求的费用敏感度渗透到每个细节。

4. 子进程隔离防止状态污染

压缩可能发生在主线程或 forked agent 中。压缩后的清理代码通过 querySource 区分：子 agent 的压缩不会重置主线程的模块级状态（microcompact 注册表、context collapse 提交日志等）。否则子 agent 压缩 → 清除主线程状态 → 主线程下次请求时 context collapse 丢失所有已保存的折叠。

5. 不要追求完美，要追求足够好

电路断路器接受"有时候就是不行"。Session Memory Compact 可能赶上提取还没完成，那就 fallback。Compact prompt 的 analysis 块是"草稿纸"——即使格式不完美，系统也能剥离后只剩 summary。PTL 重试最多 3 次，不行就放弃。每个不完美之处都有一个 fallback，组合起来就是一个健壮的系统。
