一、架构总览：七层递进式防线

Context Compaction 不是单一机制，而是七层递进式防线。每层比上一层代价更高，但能释放更多上下文空间。核心设计原则：轻量操作优先，让后续层可能不需要触发。

query.ts 每轮循环（每次 API 调用前） ┌──────────────────────────────────────────────────────────────┐ │ ① Snip Compact 剪断边界之前的历史消息 │ │ ↓ tokensFreed 传递给后续阈值计算 │ │ ② Tool Result Budget 替换超大工具结果内容 │ │ ↓ │ │ ③ Microcompact 清除旧工具结果 │ │ ├─ Time-based: 超过 60 分钟空闲 → 内容清除 │ │ └─ Cached: API cache_edits 删除（保持缓存热度） │ │ ↓ │ │ ④ Context Collapse 分级折叠上下文块（与 autocompact 互斥）│ │ ↓ │ │ ⑤ Autocompact 决策点 │ │ ├─ trySessionMemoryCompaction() → 零 LLM 调用 │ │ └─ compactConversation() → LLM 生成摘要 │ │ │ │ ⑥ API 调用 → 若返回 413 (prompt too long): │ │ ├─ Context Collapse drain → 排空折叠队列 │ │ └─ Reactive Compact → 紧凑摘要 + 保留尾部 │ └──────────────────────────────────────────────────────────────┘

前三层（snip、tool budget、microcompact）在 autocompact 决策之前运行。如果它们释放的 token 足够让用量降到阈值以下，autocompact 就不会触发——相当于"先清扫再判断是否要大扫除"。

二、何时决策压缩？—— Autocompact 阈值体系

核心逻辑位于 src/services/compact/autoCompact.ts。

2.1 阈值计算链

// 第 1 步：有效上下文窗口
effectiveWindow = min(模型窗口, CLAUDE_CODE_AUTO_COMPACT_WINDOW) - 20K
//                    ↑                                    ↑
//              默认 200K                         为 compact 输出预留

// 第 2 步：Autocompact 触发阈值
autoCompactThreshold = effectiveWindow - 13K  (AUTOCOMPACT_BUFFER_TOKENS)

// 以 200K 模型为例：
//   effectiveWindow      = 200K - 20K = 180K
//   autoCompactThreshold  = 180K - 13K = 167K
//   → token 用量达到 ~167K 时触发 autocompact

2.2 多级警告体系

2.3 每轮循环的检查顺序

在 query.ts 的主循环中，每次 API 调用前依次执行：

  1. getMessagesAfterCompactBoundary() — 裁剪掉旧压缩边界之前的消息（src/utils/messages.ts:4643）
  2. applyToolResultBudget() — 替换超大工具结果内容
  3. snipCompactIfNeeded() — 剪断历史
  4. microcompactMessages() — 先时间触发判断，再缓存编辑判断
  5. contextCollapse.applyCollapsesIfNeeded() — 投影折叠视图
  6. autoCompactIfNeeded() — 这才是 autocompact 的决策点

2.4 不触发的条件（守卫）

以下情况 shouldAutoCompact() 返回 false，即使 token 用量超过阈值也不会触发：

  • querySource 是 session_memory 或 compact — 防止 forked agent 递归死锁
  • querySource 是 marble_origami — 与 Context Collapse 的模块级状态冲突
  • DISABLE_COMPACT / DISABLE_AUTO_COMPACT 环境变量已设置
  • 用户配置中 autoCompactEnabled === false
  • REACTIVE_COMPACT 模式下若 GrowthBook flag 让 reactive 完全接管
  • CONTEXT_COLLAPSE 启用时 — collapse 自己管理 headroom，autocompact 会与它竞争

为什么 collapse 和 autocompact 互斥？ Autocompact 在 ~93% 触发（effective-13K），恰好在 collapse 的 commit-start (90%) 和 blocking (95%) 之间。两者同时启用，autocompact 会在 collapse 来得及保存细粒度上下文之前用一个大摘要覆盖所有内容。

三、无限增长怎么办？—— 四层兜底策略

用户不断处理同一个 session，token 最终一定会超出窗口。系统有四层兜底：

3.1 电路断路器（Circuit Breaker）第一道防线

MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3

连续 3 次 autocompact 失败后，停止重试。Code comment 指出：1,279 个 session 曾有 50+ 次连续失败（最多 3,272 次），每天浪费约 25 万次 API 调用。

// autoCompact.ts 第 260-265 行
if (tracking?.consecutiveFailures !== undefined &&
    tracking.consecutiveFailures >= MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES) {
  return { wasCompacted: false } // 断路器跳闸
}

3.2 Compact API 自身的 PTL 重试 第二道防线

compact API 调用本身也可能 Prompt Too Long（要总结的消息太多了）。此时按 API round 分组，从最老的一组开始丢弃，最多重试 MAX_PTL_RETRIES = 3 次。fallback 方案：丢弃 20% 的 API round 组。

3.3 Reactive Compact（413 反应式压缩）第三道防线

当所有前置压缩都未能阻止 413 错误时，系统不立即显示错误给用户：

API 返回 413 │ ├─ streaming loop withhold（暂扣）错误，不显示 │ ├─ Step 1: Context Collapse drain │ 排空所有 staged 折叠 → 成功? → retry API │ ↓ 失败或已 drain 过 │ ├─ Step 2: Reactive Compact │ 紧凑摘要 + 保留尾部消息 → 成功? → retry API │ ↓ 失败 (hasAttemptedReactiveCompact = true) │ └─ Step 3: 彻底放弃 → 显示 "Prompt is too long" 给用户 → 不触发 stop hooks（防止 hook → 注入更多 token → 413 → 死循环）

3.4 Blocking Limit 最终拦阻

当 token 用量达到 effectiveWindow - 3K 且所有恢复手段都失败后，系统阻止继续对话，用户必须手动 /compact 或开启新 session。

四、丢弃策略：规则驱动 vs 模型决策

这是最核心的设计问题。答案：两者结合，各司其职。

决策谁决定机理
哪些消息需要压缩 规则 token 阈值、保留上限（10K–40K）、最小文本消息数（5）、工具配对完整性
被压缩消息如何浓缩 LLM 模型 九维度 compact prompt 引导模型提取关键信息（不调用工具）
压缩后保留哪些文件 规则 最多 5 个最近读取文件，总预算 50K tokens，单文件上限 5K
压缩后保留哪些 Skill 规则 最近调用的 skills，单 skill 上限 5K，总预算 25K
Microcompact 清除哪些工具结果 规则 只保留最近 N 个（默认 5），只清除 8 种白名单工具类型
Compact API 自身 PTL 丢弃什么 规则 按 API round 分组，从最老组开始丢弃，最多 3 次重试

4.1 模型决策：Compact Prompt 九维度

Full Compact 触发时，一个禁止所有 tool use 的 LLM 生成摘要。九维度结构：

  1. Primary Request and Intent — 用户的主要意图
  2. Key Technical Concepts — 涉及的技术概念、框架
  3. Files and Code Sections — 操作过的文件 + 完整代码片段 + 为什么重要
  4. Errors and Fixes — 错误 + 修复方法 + 用户反馈
  5. Problem Solving — 已解决问题 + 进行中的排错
  6. All User Messages — 所有非工具结果的用户消息（理解 feedback 和意图变迁的关键）
  7. Pending Tasks — 待处理任务
  8. Current Work — 最近消息的精确描述（含文件名和代码）
  9. Optional Next Step — 可选的下一步（含原文引用确认）

设计亮点： Prompt 先让模型输出 <analysis> 草稿块，再输出 <summary>。formatCompactSummary() 剥离 analysis 块，只保留 summary 放入上下文。analysis 是给模型的"草稿纸"，提高摘要质量但不占用上下文。

4.2 规则决策：Session Memory Compact 的消息保留算法

Session Memory Compact 完全是规则驱动，不做 LLM 调用，直接使用后台预提取的会话笔记：

// sessionMemoryCompact.ts — 消息保留配置
const DEFAULT_SM_COMPACT_CONFIG = {
  minTokens: 10_000,          // 至少保留 10K tokens
  minTextBlockMessages: 5,    // 至少保留 5 条文本消息
  maxTokens: 40_000,          // 保留硬上限 40K tokens
}

// 算法：
// 1. 从 lastSummarizedMessageId 之后开始计算
// 2. 如果 tokens < minTokens 或消息数 < minTextBlockMessages
//    → 向前扩展（包含更多消息）
// 3. 如果 tokens ≥ maxTokens → 停止
// 4. adjustIndexToPreserveAPIInvariants():
//    → 确保 tool_use/tool_result 配对不被拆分
//    → 确保共享 message.id 的 thinking block 不被孤立
// 5. 压缩后若仍 ≥ autoCompactThreshold → 返回 null，fallback 到 Full Compact

五、各层机制详解

5.1 Snip Compact Feature: HISTORY_SNIP

src/query.ts:396-409最先运行，从消息数组中物理剪切旧历史，不做总结

与 autocompact 不同，snip 不做总结而是直接丢弃。由于 assistant 消息中的 token usage 保留的是 snip 前的统计，snipTokensFreed 被传递给后续 autocompact 的阈值计算进行修正。

5.2 Tool Result Budget Feature Gate

src/query.ts:369-394对单个工具结果进行预算截断，在 microcompact 之前运行

如果某个工具返回了超大结果（如读取巨型文件），将其内容替换为截断版本。只修改内容，不影响缓存结构。

5.3 Microcompact — 两个独立路径

src/services/compact/microCompact.ts轻量级预请求上下文清理，不调用 API

Time-based Microcompact GrowthBook: tengu_slate_heron

  • 触发条件：距上一条 assistant 消息 ≥ gapThresholdMinutes（默认 60 分钟）
  • 操作：将旧的可压缩工具结果内容替换为 [Old tool result content cleared] 占位符
  • 只保留最近 keepRecent 个（默认 5）工具结果不被清除
  • 原理：长时间未活动 → server-side cache 已过期 → 下次请求整个 prefix 会重写 → 提前清除旧内容减小重写体积
  • 清除后同时 reset cached MC state（cache 已冷，cache_edits 不再有效）

Cached Microcompact Feature: CACHED_MICROCOMPACT

  • 使用 Anthropic API 的 cache_edits 功能，在不破坏提示缓存的前提下删除旧工具结果
  • 维护模块级全局状态：registeredTools、toolOrder、pendingCacheEdits
  • 生成的 cache_edits 块附加在下一次 API 请求中
  • 边界消息延迟到 API 响应后发出（使用真实的 cache_deleted_input_tokens）
  • 只在主线程运行：防止 forked agent 的 tool_results 污染全局状态

5.4 Context Collapse Feature: CONTEXT_COLLAPSE

src/query.ts:440-447与 autocompact 互斥的替代上下文管理方案
  • 启用时 autocompact 被抑制，由 collapse 自己管理上下文 headroom
  • ~90% token 用量 → 开始提交折叠（commit）
  • ~95% → 阻塞式等待折叠完成
  • 折叠操作是可投影的：不修改 REPL 完整历史，而是在读取时投影出折叠后视图
  • 跨轮持久化：下次循环进入时 projectView() 从提交日志重放折叠
  • 当 413 发生时，先 drain（排空）所有 staged 折叠队列

5.5 Session Memory Compact 优先尝试

src/services/compact/sessionMemoryCompact.ts零 LLM 调用的压缩路径，autocompact 和 /compact 都优先尝试

为什么优先？ Session Memory 是后台 task 持续提取的会话笔记。压缩时直接使用已有内容，省去一次 LLM API 调用。只有当 session memory 为空或压缩后仍超标时，才 fallback 到昂贵的 Full Compact。

处理两种场景：

  • 正常 case：有 lastSummarizedMessageId，只保留该 ID 之后的消息
  • Resumed session：没有 lastSummarizedMessageId 但有 session memory 内容，保留全部消息但使用 session memory 作为摘要

5.6 Full Compact — LLM 总结 最昂贵路径

src/services/compact/compact.ts核心 compact 逻辑，约 1700 行

完整流程：

compactConversation() 执行流程: 1. pre-compact hooks (用户可注入自定义指令) 2. stripImagesFromMessages() image/document → [image]/[document] 文本标记 防止图片撑爆 compact API 自身 3. stripReinjectedAttachments() 去掉会被重新注入的 skill_discovery/skill_listing 4. streamCompactSummary() ├─ Forked Agent 路径 (默认): 共享主对话 prompt cache → ~98% 命中率 └─ Streaming 路径: fallback (模型不兼容时) 5. 5.7 Reactive Compact — 413 兜底 最后防线

src/query.ts:1062-1183API 返回 413 后的恢复流程
  • 413 错误在 streaming loop 中被 withhold（暂扣），不立即显示给用户
  • 先尝试 Context Collapse drain（如果 collapse 启用）
  • 再尝试 Reactive Compact — 生成紧凑摘要并丢弃超出部分
  • hasAttemptedReactiveCompact flag 防止无限循环
  • 特别处理 media-size 错误（图片/PDF 太大），通过 stripImages 后重试
  • 所有手段耗尽后才向用户显示错误
  • 不触发 stop hooks：否则 hook → 注入 tokens → 413 → hook 注入 → 死循环

七、设计洞察

7.1 Forked Agent + Cache Sharing

Compact API 调用复用主对话的 prompt cache（共享 system prompt + tools + messages prefix），达到 ~98% cache 命中率。没有 cache sharing，每次 compact 将产生 ~200K token 的 cache creation 成本。

7.2 子进程隔离（Subagent Isolation）

runPostCompactCleanup() 检查 querySource，只为 main-thread 重置模块级状态。子 agent 的 compact 不会清除主线程的 microcompact 状态、context collapse 状态等。

7.3 工具配对完整性（Invariant Preservation）

adjustIndexToPreserveAPIInvariants() 是一个精心设计的函数：

  • 如果保留的 user 消息中有 tool_result，确保对应的 tool_use 也在保留范围内
  • 如果保留的 assistant 消息与前面的消息共享 message.id（streaming 产生的分片），一起保留以确保 thinking block 不丢失
  • 索引 floor 在 compact boundary（磁盘不连续性），防止 loader 的 tail→head walk 跳过 inner preserved messages

7.4 压缩后的无缝衔接

压缩后的 summary 消息包含精确指引：

  • "This session is being continued from a previous conversation that ran out of context."
  • Transcript 文件路径（让模型需要时可以读取完整历史）
  • Autocompact 模式："Continue ... without asking the user any further questions. Resume directly — do not acknowledge the summary."
  • Proactive mode 特殊提示：这不是第一次 wake-up，不要问候用户

7.5 Skill 内容跨压缩保持

调用的 skill 内容有意不在压缩时清除（runPostCompactCleanup 跳过 reset 已调用的 skill names）。每次压缩后重新注入最近调用 skills 的内容，确保 agent 在压缩后仍知道如何执行特定领域任务。

7.6 压缩警告 UI 抑制

compactWarningState.ts 追踪压缩后 "context 剩余 X%" 警告是否应抑制。压缩成功后抑制，因为下一次 API 响应前准确的 token 计数还不可用。

7.7 压缩中的 Token 估算

压缩阈值检查使用 tokenCountWithEstimation()：取上次 API 响应的真实 token 计数 + 对之后新增消息的估算（padding 4/3 以保守估计）。这避免了每次都要等 API 响应才知道是否需要压缩。
