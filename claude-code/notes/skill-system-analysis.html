Claude Code Skill 系统设计分析

多来源、统一类型、延迟加载的插件机制
来源: src/skills/ + src/tools/SkillTool/ + src/commands.ts 核心文件: ~15个 分析日期: 2026-05-31

Summary — 整体架构

Skill 系统是 Claude Code 的可扩展任务能力层。它将领域知识和操作流程封装为 skill，模型通过 Skill 工具按需调用。架构核心思想是 "元数据先行，内容按需"——启动时只加载 YAML frontmatter 元数据（名称、描述、触发条件等），完整 SKILL.md 内容仅在调用时才展开。

五层来源，统一抽象

┌──────────────────────────┐ │ Command 统一类型 │ │ (PromptCommand / prompt) │ └──────────────────────────┘ ▲ ┌───────────┬───────────┼───────────┬───────────┐ │ │ │ │ │ Bundled File-based Plugin MCP Dynamic (编译进CLI) (/skills/) (市场插件) (MCP协议) (会话发现) 加载时机: 启动同步 启动异步 启动异步 运行时 会话中 存储位置: 内存数组 磁盘目录 插件目录 MCP服务器 .claude/

Details — 关键机制详解

1. 初始化流程

Skill 初始化分三个阶段，从同步注册到异步加载再到每轮注入：

阶段一：同步注册 main.tsx 最早阶段

main.tsx (line ~1925) ├─ initBuiltinPlugins() → 注册内置插件定义到 plugin registry └─ initBundledSkills() → registerBundledSkill() 推入 bundledSkills[] 数组 ├─ update-config ├─ keybindings ├─ verify ├─ debug ├─ simplify ├─ review ├─ loop ├─ claude-api ├─ remember ├─ skillify └─ ... (共 ~16 个)

阶段二：异步加载 memoized

getCommands(cwd) — memoized by cwd └─ loadAllCommands(cwd) ├─ getSkills(cwd) ←── 并行 │ ├─ getSkillDirCommands(cwd) → 扫描 managed/user/project/add-dir │ ├─ getPluginSkills() → 从已启用插件加载 │ ├─ getBundledSkills() → 内存数组快照 │ └─ getBuiltinPluginSkillCommands() → 内置插件转换 ├─ getPluginCommands() → 非 skill 类插件命令 └─ getWorkflowCommands(cwd) → workflow 脚本命令

阶段三：每轮注入 skill_listing attachment

collectAttachments(messages, context) └─ getSkillListingAttachments(context) ├─ 过滤: type='prompt' + 有描述 + 非 builtin + 非 disableModelInvocation ├─ 追踪: sentSkillNames 记录已发送, 每轮只发新 skill └─ 格式化: formatCommandsWithinBudget(commands, contextWindowTokens) ├─ 预算: 上下文窗口的 1% (~8000 chars) ├─ 截断: 单条描述上限 250 chars ├─ bundled skill 永不被截断 └─ 超出预算时非 bundled 描述逐步缩短 → 极端情况仅保留名称

关键设计：getSkillDirCommands() 和 loadAllCommands() 都是 memoized — 同一次会话不会重复扫描文件系统。chokidar 文件监听器在 SKILL.md 变化时清缓存，实现热更新。

2. 文件系统 Skill 的加载与解析

目录扫描顺序 (first-wins 优先级)

managed (policy) → user (~/.claude/skills/) → project (.claude/skills/ 向上遍历) → additional (--add-dir) → legacy (commands/ 目录兼容)

SKILL.md 格式

---
description: 一句话描述
when_to_use: 帮助模型决定何时调用的提示
allowed-tools: [Bash, Read, Edit]
arguments: [name: 参数名, description: 参数说明, required: true]
model: sonnet           # 可选: opus | sonnet | haiku | inherit
context: fork           # 可选: inline(默认) | fork
agent: general-purpose  # fork 时使用的 agent 类型
effort: high            # thinking effort 级别
paths: ["src/**/*.ts"] # 条件激活的 glob 模式
user-invocable: true    # 用户可否通过 /skillname 调用
disable-model-invocation: false
hooks:                  # 生命周期钩子
  PostToolUse: [...]
version: 1.0
---

# Skill 内容 (markdown body)
这里是 skill 的完整指令和领域知识...
支持 ${ARGUMENTS} 替换和 !`shell 命令` 内联执行

3. Bundled Skills 全景

Bundled skills 是编译进 CLI 二进制文件中的 skill，在 main.tsx 启动时通过 initBundledSkills() 同步注册到内存数组，不需要文件系统扫描。与 file-based skill 的关键区别：

维度BundledFile-based
存储位置代码中 (src/skills/bundled/*.ts)磁盘目录 (.claude/skills/)
加载时机启动时同步注册启动时异步扫描
资源文件files: Record<string, string> 延迟提取到磁盘SKILL.md 直接读磁盘
skill_listing 优先级描述永不被截断预算不足时描述可被截断或移除
可否删除不可删除（核心功能）可删除

4. Skill 被调用时发生了什么

核心原则：元数据批量注入，内容按需加载。 下面是一个完整调用链路：

模型决定调用 Skill( skill="review", args="." ) │ ├─ 1. validateInput() │ ├─ 检查 skill 名非空，去掉前导 / │ ├─ 实验性: 远程 canonical skill 检查 (_canonical_<slug>) │ └─ findCommand(name) → 验证存在、type='prompt'、无 disableModelInvocation │ ├─ 2. checkPermissions() │ ├─ 检查 deny 规则 (拒绝列表) │ ├─ 检查 allow 规则 (允许列表, 支持通配符如 review:*) │ ├─ "仅安全属性" 自动允许 (无 hooks / allowedTools) │ └─ 否则 → 弹出权限对话框询问用户 │ └─ 3. call() ├─ recordSkillUsage(name) → 更新使用频率跟踪 (7天半衰期指数衰减) │ ├─ context === 'fork' ? │ └─ executeForkedSkill() │ ├─ prepareForkedCommandContext() → 构建子 agent 上下文 │ ├─ runAgent() → 独立 token 预算 + 工具集 │ └─ 返回 { agentId, result } │ └─ context === 'inline' (默认) ? └─ processPromptSlashCommand(name, args, commands, context) ├─ command.getPromptForCommand(args, context) ★ 此时才加载完整内容 │ ├─ 读取 SKILL.md body │ ├─ 注入 "Base directory for this skill: /path" │ ├─ substituteArguments() → 替换 ${ARGUMENTS} │ ├─ 替换 ${CLAUDE_SKILL_DIR} 和 ${CLAUDE_SESSION_ID} │ └─ executeShellCommandsInPrompt() → 执行 !`cmd` 内联 shell │ ├─ registerSkillHooks(hooks) → 注册 frontmatter 定义的钩子 ├─ addInvokedSkill(name, content) → 注册到压缩保护列表 └─ 返回 { newMessages, contextModifier } └─ contextModifier: { allowedTools, model, effort } 更新后续对话

Inline vs Fork — 设计决策

Inline 默认

  • SKILL.md 内容注入当前对话流
  • 共享主对话的上下文窗口
  • 适合轻量指令、模板展开
  • 可修改 contextModifier (允许工具/模型/effort)

Fork 隔离执行

  • 独立子 agent，独立 token 预算
  • 不污染主对话上下文
  • 适合复杂多步操作
  • 通过 runAgent() 异步执行，返回结果摘要
  • Analytics 标记 execution_context: 'fork'

5. Skill 的 Artifact 加载策略

核心洞察：不是一次性全部 load。 系统分两层加载，严格遵循"最小上下文污染"原则。

层级时机加载内容大小控制
L1 元数据 启动时 + 每轮对话 name + description + whenToUse (frontmatter 解析结果) 上下文窗口 1% (~8000 chars)，单条 250 chars 硬上限
L2 完整内容 Skill 工具被调用时 完整 SKILL.md body + shell 命令执行结果 + 变量替换 无硬限制，但 fork 模式有子 agent token 预算
L3 附件资源 Skill 调用时 (bundled) bundled skill 的 files: Record<string, string> 延迟提取到磁盘 按需提取，不预加载

skill_listing 的预算策略

formatCommandsWithinBudget(commands, contextWindowTokens): 1. 计算总预算 = contextWindowTokens × 4 chars/token × 1% 后备默认: 200k × 4 × 1% = 8000 chars 2. 尝试完整描述 (name + description + whenToUse) → 如果在预算内 → 全部输出 3. 否则: ├─ bundled skills → 完整描述 (优先保证) ├─ 非 bundled → 剩余预算 / 数量 = maxDescLen ├─ maxDescLen ≥ 20 → 按 maxDescLen 截断描述 └─ maxDescLen < 20 → 非 bundled 只输出名称 (极端情况) 4. 去重: sentSkillNames 集合跟踪已发送, 每轮只发送 newSkills (首次出现的 skill)

6. 多 Skill 冲突处理

去重分两层

层级机制范围策略
文件级 getFileIdentity(filePath) — realpath 解析 symlink 同一加载来源内 (managed/user/project...) first-wins, 后续相同 realpath 跳过 + debug log
名称级 findCommand() — 数组顺序查找, 返回第一个匹配 跨来源 (bundled → builtinPlugin → file → workflow → plugin) 隐式覆盖, 无警告
动态级 baseCommandNames.has(s.name) 检查 动态 skill vs 已加载 skill 同名跳过, 不覆盖已有

合并顺序决定了名称冲突时的优先级：

loadAllCommands() 返回数组顺序: [...bundledSkills, ...builtinPluginSkills, ...skillDirCommands, ...workflowCommands, ...pluginCommands, ...pluginSkills, ...COMMANDS()] findCommand(name) → Array.find(c => c.name === name || c.aliases?.includes(name)) → 前面的来源优先级更高

潜在风险：

  • 同一来源内两个 skill 同名：第二个被 findCommand 忽略，无警告
  • 两个 skill 声明了重叠的 when_to_use 触发条件：系统不做语义冲突检测，模型自行判断
  • 条件 skill (paths:) 存储于 conditionalSkills Map，激活后移入 dynamicSkills，不与无条件 skill 冲突
  • 如果 project 级别定义了与 bundled skill 同名的 skill，bundled 版本优先（因为它在数组最前面）

7. 条件 Skill 与动态发现

条件 Skill paths: frontmatter

带有 paths: ["src/**/*.sql"] frontmatter 的 skill 启动时进入 conditionalSkills Map（休眠）。当模型读取或写入匹配 glob 的文件时，activateConditionalSkillsForPaths() 将其激活并移入 dynamicSkills。

动态 Skill 发现 会话中

当文件操作发生时，discoverSkillDirsForPaths() 从操作的文件路径向上遍历至 cwd，寻找 .claude/skills/ 目录。新发现的目录通过 addSkillDirectories() 加载，较深路径覆盖较浅路径。发现后触发 clearCommandMemoizationCaches() 刷新命令列表。

Conclusion — 回顾与串联

Summary 中的架构图描述了五层来源如何汇入统一的 Command 抽象。这五层来源在 Details 第 1 节的三阶段初始化中被依次加载和组合。

Details 第 2 节解释了文件系统 skill 的 SKILL.md 格式和解析流程——这是五层中"File-based"来源的具体实现。第 3 节展示了调用链路，揭示了 context: inline|fork 的分叉执行模式。

第 4 节回答了核心问题：artifact 不是全量预加载的。L1 元数据（name + description + whenToUse）在启动时批量注入 skill_listing attachment，受 1% 上下文窗口预算严格约束。L2 完整内容仅在 getPromptForCommand() 调用时才加载——这是"元数据先行，内容按需"架构的关键。

第 5 节回答冲突问题：文件级通过 realpath 去重（first-wins），名称级通过数组顺序隐式解决（无警告），没有语义级别的冲突检测。第 6 节的动态发现和条件 skill 是对静态加载的补充，让 skill 系统能响应会话中的文件操作。

一句话总结：Skill 系统 = 多来源统一抽象 + 元数据预载/内容延迟 + inline/fork 双模执行 + 文件级去重/名称级隐式覆盖。它不是"把所有 skill 灌给模型"，而是"让模型知道有什么 skill 可用，用时再加载"。
