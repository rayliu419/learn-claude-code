一、总览

Claude Code 的自治智能体机制构建在 In-Process Teammate 的多轮工作循环之上。生产代码中的"自治"不是教学版 s17 的 WORK → IDLE → poll → claim → WORK 显式阶段切换，而是 runInProcessTeammate() 主循环中 runAgent()（工作）→ waitForNextPromptOrShutdown()（空闲轮询）的自然交替。

二、主循环：WORK → IDLE 自然交替

生产版的自治循环不是通过"模型主动调用 idle 工具"进入空闲阶段，而是由 runInProcessTeammate() 的 while 循环天然实现：

runInProcessTeammate() ← 在独立的 AsyncLocalStorage 上下文中 │ ├─ buildSystemPrompt() ← 含 TEAMMATE_SYSTEM_PROMPT_ADDENDUM ├─ tryClaimNextTask() ← 立即尝试认领（让 UI 从一开始就显示活动） │ └─ while (!abort && !shouldExit) ← 主循环 │ │ ═══════ WORK PHASE ═══════ ├─ create currentWorkAbortController ← 仅中断本轮（Escape），不杀死队友 ├─ set isIdle: false ← 标记为工作中 ├─ runAgent() ← 完整的 agent loop │ └─ 共享核心 API 基础设施 │ (query + runAgent + tool dispatch) │ │ ═══════ WORK COMPLETE ═══════ ├─ set isIdle: true ← 标记为空闲 ├─ sendIdleNotification(leader) ← 通知 Leader │ └─ idleReason: 'available' │ 'interrupted' ← Escape 中断 │ 'failed' ← 运行时异常 │ │ ═══════ IDLE PHASE ═══════ └─ waitForNextPromptOrShutdown() ← 阻塞直到有工作 ├─ pendingUserMessages? ← 最高优先级（Leader 直接 push） ├─ shutdown_request? ← 优先于普通消息 ├─ leader messages? ← 优先于 peer 消息 ├─ peer messages? ← FIFO └─ tryClaimNextTask() ← 最低优先级 │ └─ 找到可认领任务 → 返回 new_message 否则 → 继续下一轮 500ms 轮询

三、空闲轮询引擎：waitForNextPromptOrShutdown

这是生产版中"自治"行为的核心技术。它每隔 500ms 检查四种来源的输入，按优先级返回：

waitForNextPromptOrShutdown(identity, abortController, taskId, ...) │ │ 500ms 循环（无超时，直到 abort） │ ├─ [1] pendingUserMessages[] ← 最高优先级 │ └─ Leader 通过 injectUserMessageToTeammate() 直接 push 的消息 │ └─ 零延迟，不需要 mailbox 轮询 │ └─ 返回 { type: 'new_message', from: 'user' } │ ├─ [2] Mailbox shutdown_request 扫描 ← 第二优先级 │ └─ 扫描所有未读消息，优先检测 shutdown_request │ └─ 防止 peer-to-peer 消息洪泛导致 shutdown 饥饿 │ └─ 返回 { type: 'shutdown_request' } │ ├─ [3] Mailbox leader → peer 优先级 ← 第三优先级 │ └─ 先找来自 team-lead 的未读消息 │ └─ 未找到则找第一个未读消息（FIFO） │ └─ 返回 { type: 'new_message', from: sender } │ └─ [4] tryClaimNextTask(taskListId, agentName) ← 最低优先级 ├─ listTasks() 获取完整任务列表 ├─ findAvailableTask(): pending + 无 owner + 无阻塞 ├─ claimTask() 原子认领（proper-lockfile） └─ 认领成功 → formatTaskAsPrompt() └─ 返回 { type: 'new_message', from: 'task-list' }

设计关键：这种按来源的优先级设计确保了"明确的指令（Leader push / mailbox 消息）总是优先于自治扫描到的任务"。这与教学版"先看邮箱，再看任务板"的顺序一致，但增加了 shutdown 和 pendingUserMessages 两个更高优先级路径。

四、任务认领机制

可认领条件

findAvailableTask(tasks: Task[]): Task | undefined │ ├─ task.status === 'pending' ← 未开始 ├─ !task.owner ← 无人认领 └─ task.blockedBy 全部 resolve ← 无前置阻塞 └─ blockedBy 中的每个 ID 在 tasks 中的状态 != 'completed' → 该任务仍 unresolved → 跳过此 task

与教学版的差异：

  • 教学版有 claim_role / required_role 角色过滤，生产版暂时没有角色匹配逻辑（所有 teammate 使用同一个 taskListId）
  • 教学版有 claim_source: 'auto' | 'manual' 记录，生产版通过 task owner 字段跟踪
  • 教学版有 claim_events.jsonl 日志，生产版通过 task 文件的 owner 回写 + lockfile 实现原子性

原子认领

claimTask() 使用 proper-lockfile 确保原子性，防止竞态：

claimTask(taskListId, taskId, claimantAgentId) ├─ 检查任务文件存在性 ├─ lockfile.lock(taskPath) ← 独占锁 ├─ 读当前任务状态 ├─ 检查 owner（已有人认领？） ├─ 检查 status（已完成？） ├─ 检查 blockedBy（仍有未完成阻塞？） ├─ updateTaskUnsafe(taskId, { owner }) ← 回写 └─ release lock

双重认领时机

  1. 启动时（line 1019）：tryClaimNextTask() 立即执行一次，让 UI 从开始就显示活动
  2. 空闲轮询时（line 854）：waitForNextPromptOrShutdown() 自动调用，最低优先级

七、Idle 与 Task 系统的结合

生产代码中 tryClaimNextTask() 所操作的 Task 是 durable task（utils/tasks.ts），与教学版 s12 的 task record 对应：

// Durable Task 数据结构 (utils/tasks.ts: TaskSchema) Task { id: string subject: string description?: string status: 'pending' | 'in_progress' | 'completed' | 'failed' owner?: string ← 认领后写入 blockedBy: string[] createdBy?: string createdAt: number updatedAt: number completedAt?: number tags?: string[] metadata?: Record<string, unknown> } // 认领结果类型 ClaimTaskResult = | { success: true, task: Task } | { success: false, reason: 'task_not_found' | 'already_claimed' | 'already_resolved' | 'blocked', task?: Task, blockedByTasks?: string[] }

注意：生产版的 Task 与教学版有几个差异：(1) 没有 claim_source 字段标记 auto/manual；(2) 没有 claim_role / required_role 角色匹配；(3) 没有专门的 claim event 日志——所有信息通过 owner 字段和 updatedAt 推导。

九、总结

自治智能体设计哲学："不是让 agent 乱跑，而是让它在清晰规则下自己接住下一份工作。"

生产代码的自治行为不是通过教学版中"模型主动调用 idle 工具"实现的显式阶段切换，而是 runInProcessTeammate() 主循环的自然属性——每次 runAgent() 完成后自动进入 waitForNextPromptOrShutdown() 轮询状态。教学版追求的是"展示自治的完整概念"，生产版追求的是"可靠地保持活跃、高效地分发工作"。最大的差异在于生产版没有空闲超时（teammate 无限期存活）、没有角色匹配（所有 teammate 共享同一 task list）、没有显式身份重注入（身份通过系统提示词持久化）。

关键设计权衡

活跃性✅ 无限期存活，不因空闲超时丢失 teammate（节省 spawn 开销）
资源占用⚠️ 500ms 轮询 + mailbox I/O 持续消耗，长时间空闲时浪费
可靠性✅ proper-lockfile 确保原子认领，多 teammate 不会冲突抢任务
响应性✅ pendingUserMessages 零延迟路径 + 邮箱 500ms 最大延迟
简洁性✅ 不需要显式的"空闲阶段"状态机，while 循环自然实现
任务分发⚠️ 无角色匹配，所有 teammate 无条件竞争同一任务池
