Claude Code MCP & Plugin 系统设计分析

六大 Transport、七级 Config Scope、动态工具命名与路由、Plugin 三层架构、权限统一入口

mcp__{server}__{tool} 6 Transport + 7 Scope isMcp: true 动态工具 Plugin 三层：发现→连接→调用

一、总览

Claude Code 的 MCP & Plugin 系统是一套外部能力接入框架：Plugin 负责"发现"（从文件系统、市场、CLI 发现配置），MCP 负责"连接"（通过 6 种 Transport 连接外部进程），Tool 负责"调用"（通过统一的前缀名路由到对应 Server 执行）。教学版 s19 的 "MCPClient + PluginLoader + MCPToolRouter" 三层在生产版中对应为"3348 行的 client.ts + PluginLoader + MCPTool(isMcp=true) 动态构建"。

二、MCP 工具命名体系

生产版使用 mcp__{serverName}__{toolName} 三层命名，通过 mcpStringUtils.ts 统一处理：

// 构建全限定名 buildMcpToolName(serverName, toolName) → "mcp__" + normalizeNameForMCP(serverName) + "__" + normalizeNameForMCP(toolName) // 解析全限定名 mcpInfoFromString("mcp__postgres__query") → { serverName: "postgres", toolName: "query" } // 获取前缀 getMcpPrefix("postgres") → "mcp__postgres__" // 权限检查名称 getToolNameForPermissionCheck(tool) → tool.mcpInfo ? buildMcpToolName(...) : tool.name // MCP 工具使用全限定名以便 deny 规则不与同名的 native 工具冲突

SDK 优化：对于 @modelcontextprotocol/sdk 类型的 MCP server，如果工具名不与其他原生工具冲突，可以跳过 mcp__ 前缀，让 SDK 工具的显示名称更简洁。

四、Config Scope（7 级）

生产版的 MCP Server 配置不是单层 JSON，而是 7 级 scope 可叠加：

ConfigScope = 'local' | 'user' | 'project' | 'dynamic' | 'enterprise' | 'claudeai' | 'managed' 优先级（高 → 低）： dynamic (运行时 CLI/SDK) local (settings.local.json) user (~/.claude/settings.json) project (.claude/settings.json) enterprise (企业策略) managed (托管) claudeai (claude.ai 同步)

六、Plugin 组件结构

my-plugin/ ├── plugin.json # 清单：name, version, mcpServers, ... ├── commands/ # 自定义斜杠命令 │ ├── build.md # /build 命令（提示词驱动） │ └── deploy.md ├── agents/ # 自定义 AI agent │ └── test-runner.md # agent 定义（type: "agent"） └── hooks/ # Hook 配置 └── hooks.json # Hook 定义

Plugin 组件由 pluginLoader.ts 统一发现和验证，每个组件类型有不同的加载路径：

  • commands → loadPluginCommands.ts
  • agents → loadPluginAgents.ts
  • hooks → loadPluginHooks.ts
  • mcpServers → mcpPluginIntegration.ts

七、MCPTool 与原生工具的共享生命周期

LLM 产出 tool_use { name: "mcp__postgres__query", input: {...} } │ ├─ 权限检查 │ └─ MCPTool.checkPermissions() → PermissionResult │ └─ behavior: 'passthrough'（走通用权限系统） │ ├─ 工具分发 │ └─ toolMatchesName("mcp__postgres__query") → 匹配 MCPTool │ ├─ MCPTool.call() │ └─ client.callTool({ name: "query", args }) │ ├─ 结果处理 │ ├─ content 标准化 → tool_result │ ├─ 大结果截断 (truncateMcpContentIfNeeded) │ ├─ 二进制内容持久化 (persistBinaryContent) │ └─ 图片缩放 (maybeResizeAndDownsampleImageBuffer) │ └─ 错误处理 ├─ McpAuthError → client 状态标记 needs-auth ├─ 超时 → retry / error └─ 连接断开 → reconnectMcpServer()

八、权限与安全

三层安全防线

  1. Server 批准 — MCPServerApprovalDialog：用户首次运行 MCP Server 时确认（防止任意命令执行）
  2. 工具权限 — MCPTool.checkPermissions() → behavior: 'passthrough' 委托给通用权限系统
  3. 命名隔离 — mcp__ 前缀确保 MCP 工具不会与原生工具命名冲突

教学版与生产版的权限差异：教学版的 CapabilityPermissionGate 有一个 risk 分层（read→自动允许 / write→询问 / high→确认）；生产版没有这种分层，所有 MCP 工具通过通用 permission system 统一处理，依赖 Bash/Edit/Write 等工具的单个权限规则来决定是否弹窗。

十一、总结

MCP & Plugin 设计哲学："外部能力安全、统一地接进 agent"——进入方式不同，但进入后必须回到同一条控制面和执行面。

教学版 s19 的三层模型（MCPClient + PluginLoader + MCPToolRouter）在生产版中扩展为 6 种 Transport + 7 级 Scope + 动态工具构建（isMcp:true）+ 四类 Plugin 组件 + OAuth 认证 + 完整错误恢复 的工业化框架。核心设计跨越在于：教学版把 MCP 抽象为"一个 Client 连一个 Server"，生产版处理的是"多个 Server 各自 6 种连接方式、7 级配置 Scope 叠加、工具全限定名免冲突、动态连接/断开/重连"。无论哪种 Transport 或 Scope，MCP 工具最终都归一为 isMcp: true 的 Tool 实例，走同一套 dispatch → permission → call → result 通路。

关键设计权衡

扩展性✅ 6 种 Transport + 7 级 Scope 覆盖所有部署场景
安全性✅ Server 批准 + 工具权限 + 命名隔离 三层防线
易用性✅ Plugin 自动发现 + marketplace + builtin 零配置即可用
复杂性⚠️ 3348 行的 client.ts 单文件过于集中，Transport/Scope/OAuth 等耦合在一起
灵活性✅ SDK 可跳过 mcp__ 前缀 + 同名覆盖原生，提供更自然的用户体验
鲁棒性✅ 完整断线重连 + auth 过期检测 + 结果截断 + 错误分类处理
