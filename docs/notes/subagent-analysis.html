1. Subagent 的调用触发机制

核心结论：模型自主决策，工具描述驱动

Subagent 的调用不是硬编码规则，而是通过 模型推理 + 工具描述引导 实现的。Agent 工具和其他工具（Bash、Read、Write 等）一样，注册在工具列表中提供给主模型，模型根据当前任务自行判断是否需要委托给 subagent。

触发链路

1
工具注册：AgentTool 通过 buildTool() 注册为名为 "Agent" 的工具，包含 input schema、output schema、description 和 prompt（工具描述）
2
工具描述生成：prompt.ts:getPrompt() 动态生成完整的工具描述文本，包括：可用 agent 类型列表（名称 + 能做什么 + 拥有哪些工具）、使用指南（何时用/何时不用）、示例用法、fork subagent 语义（如果 feature gate 开启）
3
模型决策：主模型在 thinking 阶段分析用户请求，根据工具描述中的 whenToUse 指引和自身判断，决定是否调用 Agent 工具
4
参数填写：模型选择 subagent_type（指定 agent 类型）、填写 description 和 prompt、可选设置 model 覆盖和 run_in_background
5
执行入口：AgentTool.call() 接收参数，路由到对应执行路径（fork / normal / swarm / remote）

关键代码位置

  • src/tools/AgentTool/AgentTool.tsx:196-238 — 工具注册，prompt() 方法生成工具描述
  • src/tools/AgentTool/prompt.ts — 完整的 prompt 生成逻辑，包含 agent 列表、使用指南、示例
  • src/tools/AgentTool/constants.ts — AGENT_TOOL_NAME = 'Agent'
设计要点：工具描述中的 whenToUse 字段不是程序化过滤规则，而是给模型的自然语言指引。例如 Explore agent 的 whenToUse 描述它适合 "快速搜索代码库"，模型阅读后自主判断当前场景是否匹配。

2. 内置 Subagent 与插件扩展

2.1 内置 Agent 清单

Agent 类型来源文件用途模型工具策略
general-purpose built-in/generalPurposeAgent.ts 通用任务：代码搜索、多步研究、复杂问题调查 inherit（默认） ['*'] — 全部工具
Explore built-in/exploreAgent.ts 快速只读代码探索，支持 "quick/medium/very thorough" 三种深度 haiku（外部）/ inherit（内部） 黑名单排除 Edit/Write/NotebookEdit/Agent/ExitPlanMode
Plan built-in/planAgent.ts 软件架构规划：探索代码库 + 设计实现方案 inherit 同 Explore（只读）
claude-code-guide built-in/claudeCodeGuideAgent.ts 回答 Claude Code CLI / Agent SDK / Claude API 相关问题，抓取官方文档 haiku Read + Glob/Grep + WebFetch + WebSearch
statusline-setup built-in/statuslineSetup.ts 配置终端状态栏（从 shell PS1 转换或自定义） sonnet Read + Edit 仅
verification built-in/verificationAgent.ts 验证实现正确性（feature gate 控制），运行测试、构建、lint，输出 PASS/FAIL/PARTIAL 判定 inherit 黑名单排除 Edit/Write/NotebookEdit/Agent/ExitPlanMode

2.2 Agent 的注册来源

getAgentDefinitionsWithOverrides() 从三个来源加载 agent：

来源source 标识加载方式优先级
Built-in 'built-in' getBuiltInAgents() 硬编码 + feature gate 控制 最低（可被覆盖）
Plugin 'plugin' loadPluginAgents() 从已启用插件的 agents/ 目录加载 .md 文件 中
Custom (User) 'userSettings' ~/.claude/agents/*.md 或 settings.json 的 agents 字段 高
Custom (Project) 'projectSettings' .claude/agents/*.md 高
Managed (Policy) 'policySettings' MDM / 远程托管策略推送 最高
覆盖规则：getActiveAgentsFromList() 按 built-in → plugin → user → project → managed 的顺序处理，同名 agent 后者覆盖前者。这允许用户和项目用自定义 agent 覆盖内置 agent。

2.3 插件如何添加 Subagent

插件通过在 agents/ 目录放置 Markdown 文件来定义 agent：

---
name: my-agent
description: Does X when Y happens
tools:
  - Read
  - Bash
  - Grep
model: haiku
color: blue
memory: project
---

You are a specialized agent that helps with...

## Your Process
1. ...
2. ...

## Guidelines
- ...

关键机制（loadPluginAgents.ts）：

  • 通过 walkPluginMarkdown() 遍历插件目录中的 .md 文件
  • agent 名称自动加插件命名空间前缀：pluginName:agentName
  • 支持 frontmatter 配置：tools, model, color, memory, background, isolation, maxTurns, skills
  • 系统提示词支持 ${CLAUDE_PLUGIN_ROOT} 变量替换
  • 安全限制：插件 agent 的 permissionMode, hooks, mcpServers frontmatter 被忽略（防止插件越权）
  • 支持 memory scope（user/project/local），自动注入 Read/Write/Edit 工具

3. 系统提示词与工具差异

3.1 系统提示词生成

每个 agent 都有独立的系统提示词，生成方式因来源不同而异：

Agent 类型提示词来源生成机制
Built-in getSystemPrompt({ toolUseContext }) 函数动态生成，可访问当前工具上下文（如 claude-code-guide 读取自定义 agent/skill/MCP 列表）
Custom (Markdown) Markdown 内容正文 frontmatter 之后的 Markdown 正文直接作为系统提示词
Plugin 插件目录中 .md 文件正文 同 Custom，但支持 ${CLAUDE_PLUGIN_ROOT} 变量替换
Custom (JSON) prompt 字段 settings.json 中 agents 对象的 prompt 字段

所有 agent 的系统提示词都会经过 enhanceSystemPromptWithEnvDetails() 处理，追加：

  • 工作目录信息（绝对路径）
  • 可用工具列表及其使用提示
  • 模型信息
  • emoji 使用指引

3.2 工具过滤机制

filterToolsForAgent() 对 subagent 的工具集进行多层过滤：

第一层：全局禁止（ALL_AGENT_DISALLOWED_TOOLS）

所有 subagent 都禁止的工具：

  • TaskOutput — 查看其他任务输出
  • ExitPlanMode / EnterPlanMode — plan mode 切换
  • AskUserQuestion — 向用户提问（subagent 不能直接交互）
  • TaskStop — 停止其他任务
  • Agent（外部用户）— 防止嵌套 subagent（内部 ant 用户除外）

第二层：自定义 Agent 额外禁止

CUSTOM_AGENT_DISALLOWED_TOOLS 在全局禁止基础上扩展。

第三层：异步 Agent 允许列表

ASYNC_AGENT_ALLOWED_TOOLS 是白名单——异步 subagent 只能使用这些工具：Read, Write, Edit, Bash, Grep, Glob, WebFetch, WebSearch, Skill, TodoWrite, NotebookEdit 等。不支持 Agent（嵌套）、AskUserQuestion、计划模式工具等交互式功能。

第四层：Agent 自身的 disallowedTools

每个 agent 定义可以声明 disallowedTools，如 Explore agent 明确禁止 Edit/Write/NotebookEdit。

MCP 工具例外：所有以 mcp__ 开头的工具在过滤中始终放行，不受上述限制。

3.3 Agent 的 Model 选择

getAgentModel() 实现分层 model 解析：

  1. 环境变量 CLAUDE_CODE_SUBAGENT_MODEL 全局覆盖
  2. 工具调用时的 model 参数（用户显式指定）
  3. Agent 定义中的 model 字段
  4. 默认值 'inherit'（继承主 agent 的模型）

特殊逻辑：如果 agent model 是 bare alias（opus/sonnet/haiku），且父 agent 也是同一 tier，则直接复用父 agent 的精确 model string，避免跨平台降级。

4. 多 Agent 协调与管理机制

4.1 整体架构

Subagent 的协调不是传统的 "前端/后端" 分离模式，而是以下执行模式的组合：

模式执行方式UI 交互适用场景
同步 (Foreground) 主 agent 等待 subagent 完成 可显示权限提示 需要结果才能继续的任务
异步 (Background) 主 agent 启动后立即返回 不可显示 UI，通过 <task-notification> 通知 独立并行任务
Fork 子 agent 继承完整对话上下文 同异步，共享 prompt cache 不希望中间输出进入主上下文的场景
Coordinator Mode 专门的协调器 + worker 池 所有 worker 都是异步的 多 worker 并行研究与实现
Swarm (Teammate) 多个 agent 组成 team，通过 tmux/iTerm2 分屏 每个 teammate 有独立终端面板 复杂多角色协作

4.2 执行流程详解

AgentTool.call() — 路由入口

AgentTool.call({ prompt, subagent_type, ... }, toolUseContext)
  │
  ├─ team_name + name 存在？
  │   └─ YES → spawnTeammate()    // Swarm 模式：启动 teammate
  │
  ├─ subagent_type 为空 + fork gate 开启？
  │   └─ YES → FORK_AGENT 路径    // Fork 模式：继承上下文
  │
  ├─ isolation === 'remote'？
  │   └─ YES → teleportToRemote()  // 远程隔离（ant-only）
  │
  ├─ shouldRunAsync？
  │   └─ YES → registerAsyncAgent() → runAsyncAgentLifecycle()
  │
  └─ NO → runAgent() 同步执行     // 标准同步 subagent

runAgent() — 核心执行引擎

这是所有 subagent 执行的统一入口。关键步骤：

  1. Model 解析：getAgentModel() 确定最终使用的模型
  2. Context 隔离：createSubagentContext() 创建独立的 ToolUseContext
    • 克隆 readFileState（文件读取缓存）
    • 创建独立的 abortController（异步 agent 完全独立，同步 agent 链接到父级）
    • setAppState 可能为 no-op（异步 agent 不能修改父级 UI 状态）
    • 嵌套 depth 递增（用于追踪调用链）
  3. 权限模式：agent 定义可覆盖权限模式（如 dontAsk），但 bypassPermissions 和 acceptEdits 始终不被覆盖
  4. 工具解析：resolveAgentTools() 根据 agent 的 tools/disallowedTools 定义过滤可用工具集
  5. MCP 初始化：initializeAgentMcpServers() 连接 agent 专属的 MCP 服务器（与父级共享 + 内联定义的专属服务器）
  6. Hook 注册：执行 SubagentStart hooks，注册 agent 的 frontmatter hooks
  7. Skill 预加载：agent 定义中的 skills 列表被预加载到初始消息中
  8. Query 循环：通过 query() 运行标准的 agentic loop（与主 agent 相同的 query 引擎）
  9. Transcript 记录：每条消息通过 recordSidechainTranscript() 持久化
  10. 清理（finally 块）：MCP 连接、session hooks、文件缓存、bash 后台任务、todos 条目

4.3 Subagent 生命周期管理

Task 系统

异步 agent 通过 LocalAgentTask 注册到全局任务系统：

  • 注册：registerAsyncAgent() 创建任务条目，分配 abortController
  • 进度追踪：ProgressTracker 跟踪 token 消耗、工具调用次数、最近活动描述
  • 状态转换：pending → running → completed / failed / killed
  • 通知：完成后通过 enqueueAgentNotification() 以 <task-notification> XML 消息通知主 agent
  • 终止：killAsyncAgent() + TaskStop 工具允许用户停止运行中的 agent

通知机制（核心关键）

任务通知不是 hook 驱动的。SubagentStop hook 与任务通知是完全独立的两个机制：

关键理解：Subagent 完全不知道通知机制的存在。它没有"发送通知"的工具，没有被要求写通知信息——它只是正常完成自己的工作、输出最终文本，然后退场。通知由外部的框架代码在 subagent 结束后自动生成。

通知发送的完整流程图：

Subagent query() 循环结束
       │
       ├─→ 1. finalizeAgentTool()
       │     从 agentMessages 提取最后一条 assistant 的文本内容
       │
       ├─→ 2. completeAsyncAgent()
       │     更新 AppState.tasks[taskId].status = 'completed'
       │
       ├─→ 3. enqueueAgentNotification()
       │     构建 XML → enqueuePendingNotification()
       │     │
       │     │  XML 内容：
       │     │  <task-notification>
       │     │    <task-id>xxx</task-id>
       │     │    <status>completed</status>
       │     │    <result>探索结果摘要...</result>
       │     │    <output-file>/path/to/output</output-file>
       │     │    <usage><total_tokens>...</total_tokens></usage>
       │     │    <worktree>...</worktree>  （如有）
       │     │  </task-notification>
       │
       ├─→ 4. 消息队列（messageQueueManager）
       │     XML 进入全局队列，优先级 'later'
       │
       ├─→ 5. 主 agent 下一轮 tool loop
       │     query.ts 调用 getQueuedCommandAttachments()
       │     → 通知被转换为 'queued_command' 附件消息
       │     → 注入到主 agent 的上下文
       │
       └─→ 6. 主 agent 模型读到通知
             解析 <result> 摘要
             如需完整结果：Read/Bash 读取 <output-file>
             如有 worktree：检查 worktree branch 上的变更

注意：步骤 1-3 在 runAsyncAgentLifecycle() 中连续执行
步骤 4-6 由主 agent 的 tool loop 在后续迭代中完成

SubagentStop Hook（独立的用户扩展点）

与此同时，框架还会触发 SubagentStop hooks，但这与任务通知完全无关：

  • 机制：agent 定义中的 hooks.Stop 在注册时自动转为 SubagentStop（registerFrontmatterHooks() 的 isAgent=true 参数）
  • 执行时机：在 query/stopHooks.ts 中，每个 turn 结束后调用 executeStopHooks()
  • 用途：用户自定义逻辑——发 Slack 通知、写审计日志、清理临时资源等
  • 独立运作：不负责也不参与任务通知的发送

Agent 名称注册表

agentNameRegistry（Map<string, AgentId>）维护 name → agentId 映射，支持：

  • SendMessage(to: "name") — 通过名称向 agent 发送消息
  • SendMessage(to: "agent-id") — 通过 ID 向 agent 发送消息
  • Resume：agent 保持完整对话上下文，可继续工作

Worktree 隔离

Agent 可通过 isolation: "worktree" 在独立 git worktree 中运行：

  • createAgentWorktree() 创建临时 worktree
  • Agent 完成后检测是否有变更（对比 HEAD commit）
  • 无变更 → 自动删除 worktree
  • 有变更 → 保留 worktree，返回路径和分支名

Prompt Cache 共享

Fork subagent 的核心优化：

  • 子 agent 继承父 agent 的完整系统提示词
  • 共享相同的 tools 数组（useExactTools: true）
  • 共享相同的 thinkingConfig
  • 子 agent 的 API 请求前缀与父 agent 字节级一致 → prompt cache hit
  • 只有最后的 directive text 不同（每个 fork 子 agent 特有）

4.4 Coordinator Mode

Coordinator mode 是一种特殊的编排模式（通过 CLAUDE_CODE_COORDINATOR_MODE=1 环境变量启用）：

  • 角色分离：Coordinator 负责理解需求、分解任务、合成结果；Worker 负责具体执行
  • 专用 agent 类型：coordinator 模式下使用 worker agent 类型（而非 general-purpose）
  • 强制异步：所有 worker 都是异步的，结果通过 <task-notification> 传递
  • 并行化：coordinator 系统提示词强调并行启动多个 worker
  • 工作流程：Research（并行 worker）→ Synthesis（coordinator）→ Implementation（worker）→ Verification（worker）
  • Continue vs Spawn：coordinator 的提示词详细指导何时继续已有 worker（SendMessage）vs 启动新 worker（Agent）
