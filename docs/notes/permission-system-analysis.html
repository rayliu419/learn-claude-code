一、系统概览

Permission 系统是 Claude Code 的安全护栏，负责在 Agent 每次调用工具前进行权限检查。 它通过多层次决策流水线（规则匹配 → 模式判断 → 工具自身检查 → 交互审批 / AI 分类器 → Hook 拦截）， 决定每个工具调用是 allow、deny 还是 ask（需要用户确认）。

系统核心设计原则：防御性安全——默认拒绝所有未明确授权的高危操作； 渐进式授权——用户可在交互中临时或永久授予权限； 安全模式自动判断——Auto 模式下使用 AI 分类器替代用户做实时决策。

一、初始化流程

权限系统在 Claude Code 启动时由 permissionSetup.ts 中的 initializeToolPermissionContext() 初始化。 启动入口在 src/bootstrap/ 的启动序列中调用。

初始化函数签名

async function initializeToolPermissionContext({
  allowedToolsCli,      // --allowed-tools CLI 参数
  disallowedToolsCli,   // --disallowed-tools CLI 参数
  baseToolsCli,         // --base-tools CLI 参数
  permissionMode,       // 来自 CLI --permission-mode 或 settings.defaultMode
  allowDangerouslySkipPermissions,
  addDirs,              // --add-dir 参数
}): Promise<{
  toolPermissionContext,
  warnings,
  dangerousPermissions,
  overlyBroadBashPermissions,
}>

初始化步骤

  1. 解析 CLI 参数：parseToolListFromCLI() 解析逗号/空格分隔的工具列表，normalizeLegacyToolName() 将旧名称（如 Task → Agent）映射到规范名称。
  2. 检测 base tools：如果指定了 --base-tools，自动 deny 所有不在基础集中的工具。
  3. 加载磁盘规则：loadAllPermissionRulesFromDisk() 从所有启用的 settings 源加载权限规则。
  4. 检测不安全规则：Auto 模式下扫描 findDangerousClassifierPermissions()，阻止会绕过分类器的过宽权限（如 Bash(*)）。
  5. 检测过宽的 Shell 规则：Ant 内部环境下检测 Bash(*) 和 PowerShell(*)。
  6. 创建上下文：applyPermissionRulesToPermissionContext() 将规则合并进 ToolPermissionContext。
  7. 添加额外工作目录：验证并添加 settings 和 CLI 指定的附加目录权限。
  8. 异步验证自动模式：verifyAutoModeGateAccess() 通过 GrowthBook 动态配置检查 auto mode 是否可用，含断路器（circuit breaker）和模型兼容性检查。

Permission 系统初始化调用链

initializeToolPermissionContext() [src/utils/permissions/permissionSetup.ts]
├─ parseToolListFromCLI 解析 allowed/disallowed/base tools
• normalizeLegacyToolName 旧名映射 (Task→Agent, KillShell→TaskStop)
├─ 检测 baseTools 集 → 自动 deny 非基础工具
├─ loadAllPermissionRulesFromDisk() [permissionsLoader.ts]
└─ 从所有 enabled setting sources 加载规则
├─ findDangerousClassifierPermissions() — auto 模式扫描
• Bash(*) / Bash(python:*) 等危险规则
• Agent(*) 绕过子代理审查
• PowerShell(iex:*) / PowerShell(Start-Process:*)
├─ applyPermissionRulesToPermissionContext()
└─ 合并磁盘规则 + CLI args → ToolPermissionContext
├─ 验证并添加 additional directories
└─ verifyAutoModeGateAccess() — 异步 GrowthBook 门控
• 断路器 (circuit breaker) 检查
• 模型兼容性检查
• 自动踢出 auto 模式 (若断路器合闸)
初始模式优先级： --dangerously-skip-permissions → --permission-mode auto (gate check) → settings.defaultMode → default

二、权限模式（Permission Modes）

权限模式定义了权限检查的整体策略。共 6 种模式：

模式外部名称含义行为
default default 默认模式 任意未配置的规则都会触发 ask，弹出对话框
acceptEdits acceptEdits 接受编辑 自动允许除了高风险操作外的所有工具调用
plan plan 规划模式 只允许只读操作，写入操作需要明确审批。进入时保存 prePlanMode
bypassPermissions bypassPermissions 全部绕过 跳过所有权限检查（高危）。可通过 Statsig 和 settings 禁用
dontAsk dontAsk 不询问 所有 ask 都被转换为 deny，自动拒绝
auto default（外部映射） 自动模式 AI 分类器替代用户做决策，Ant-only，需 GrowthBook 门控
关键设计：模式之间通过 transitionPermissionMode() 管理状态转移，自动处理 plan 模式的进出、auto 模式的激活/去激活、危险规则的剥离/恢复。

三、权限规则系统

3.1 规则来源（PermissionRuleSource）

来源说明持久化
userSettings用户全局设置 (~/.claude/settings.json)磁盘
projectSettings项目设置 (.claude/settings.json)磁盘
localSettings本地设置（gitignored）磁盘
flagSettings功能标记（只读）只读
policySettings企业策略（只读）只读
cliArgCLI 参数（如 --allowed-tools）会话
session当前会话内存会话
command命令注入（如 /permissions）只读

3.2 规则行为（PermissionBehavior）

  • allow — 允许该工具调用
  • deny — 拒绝该工具调用
  • ask — 强制弹框询问用户

3.3 规则匹配

规则值格式为 ToolName（全局匹配）或 ToolName(content)（内容级匹配）： 

// 工具级匹配
Bash                    → 匹配整个 Bash 工具
Bash(*)                 → 同上，显式通配符

// 内容级匹配
Bash(npm install)       → 只匹配 npm install 命令
Bash(npm *)             → 匹配所有 npm 开头的命令

// MCP 工具匹配
mcp__server1            → 匹配 server1 的所有工具
mcp__server1__*         → 同上，显式通配符

// Agent 类型匹配
Agent(Explore)          → 只匹配 Explore 子代理

3.4 资源权限

除工具权限外，系统还管理工作目录权限和路径安全（pathValidation.ts）。 additionalWorkingDirectories 映射维护了额外授权的工作目录列表。 关键路径（如 .git/、.claude/、.vscode/、shell 配置文件）有专门的 safetyCheck 保护，即使 bypass 模式也无法绕过。

四、权限决策流水线

核心决策函数位于 permissions.ts:hasPermissionsToUseTool() → hasPermissionsToUseToolInner()。 这是一个严格有序的判定级联：

权限决策流水线 hasPermissionsToUseToolInner()

Step 1a 整工具 deny 规则存在？ → deny
Step 1b 整工具 ask 规则存在？ → ask (sandbox 可豁免)
Step 1c 工具自身 checkPermissions() → 委托给工具
Step 1d 工具 deny 了？ → deny
Step 1e 工具需要用户交互？ → ask
Step 1f 内容级 ask 规则？ → ask (bypass 免疫)
Step 1g 安全路径检查？ → ask (bypass 免疫)
──────────────────────────── 以上对 bypass 模式也生效 ────────────────────────────
Step 2a bypass 模式？ → allow
Step 2b 整工具 allow 规则？ → allow
Step 3 passthrough 转 ask → ask
──────────────────────────── hasPermissionsToUseTool() 外层 ────────────────────────────
若 ask 且 dontAsk 模式 → deny
若 ask 且 auto 模式 → 运行 YOLO 分类器
若 ask 且 headless → PermissionRequest hook → auto-deny

工具自身检查（checkPermissions）

每个工具可以覆盖 checkPermissions(input, context) 方法，实现工具特定的细粒度检查。 例如 Bash 工具会：

  • 检查命令前缀是否匹配 allow/deny/ask 规则
  • 检测危险模式（管道到 shell、输出重定向等）
  • 返回 subcommandResults 说明每个子命令的判定

五、交互审批流程

当流水线返回 ask 时，useCanUseTool.tsx Hook 负责协调最终的用户交互。 这是整个权限系统的核心入口点，它提供了 React Hook 形式的权限检查能力。

5.1 总体协调（useCanUseTool）

useCanUseTool Hook — 权限协调入口

├─ createPermissionContext()
└─ 创建 ctx 对象 (handleUserAllow / buildAllow / cancelAndAbort / runHooks / tryClassifier ...)
├─ hasPermissionsToUseTool() → 执行 7 步判定流水线
├─ [allow] logDecision + resolve(buildAllow)
├─ [deny] logDecision + recordAutoModeDenial + resolve(deny)
└─ [ask] 分流到三种 handler：
├─ Coordinator Worker → handleCoordinatorPermission()

└─ 未解决 → 回退到交互对话框
├─ Swarm Worker → handleSwarmWorkerPermission()
├─ 尝试 classifier 自动批准
├─ mailbox 转发给 leader
└─ 注册回调等待 leader 响应
└─ Main Agent → handleInteractivePermission()

├─ 后台: PermissionRequest hooks
├─ 后台: Bash 分类器 (异步竞速)
├─ 2s 宽限期: 投机分类器 (speculative)

• 本地 Terminal 对话框
• CCR Bridge (claude.ai)
• Channel (Telegram / iMessage)
• Hook 自动决策
• Classifier 自动批准

5.2 交互式处理（handleInteractivePermission）

interactiveHandler.ts 实现了主 Agent 的交互审批流程，使用多路竞速（race）模式：

  • 本地用户：通过 ToolUseConfirm 队列在 Ink 终端渲染对话框
  • Bridge（CCR）：通过 replBridgePermissionCallbacks 发送到 claude.ai
  • Channel：通过 MCP send_message 发送到 Telegram/iMessage 等
  • Hooks：PermissionRequest hooks 异步运行
  • Bash 分类器：异步检查，自动批准后显示 3s ✓ 标记

使用 createResolveOnce 确保仅胜出一方能解决问题，防止重复授权。 用户操作有 200ms 宽限期防止误触取消分类器。

5.3 Coordinator Handler

对于 coordinator worker（后台 Agent），所有自动化检查（hooks + classifier）在显示对话框前顺序等待。 这确保后台 Agent 在不打断用户的情况下尽可能自行解决权限问题。

5.4 Swarm Worker Handler

对于 swarm worker，权限请求通过mailbox 通信机制转发给 leader 节点。 leader 的 allow/reject 决定通过回调发回 worker。同时显示"等待 leader 审批"的视觉指示。

六、Auto 模式与 AI 分类器

Auto 模式（Ant-only）是权限系统的最高级特性。它使用 AI 分类器替代人工审批每个工具调用。

6.1 架构

位于 src/utils/permissions/yoloClassifier.ts（主分类器）和 bashClassifier.ts（Bash 专用）。 分类器使用 Claude API 的 sideQuery 运行，对当前上下文和工具参数进行分析。 2 阶段架构：快速阶段 + 思考阶段。

6.2 安全护栏

  • 危险规则剥离：stripDangerousPermissionsForAutoMode() 在进入 auto 模式时自动移除过宽的 allow 规则（如 Bash(*)、Agent(*)）。
  • 安全工具白名单：某些低风险工具跳过分类器直接 allow。
  • acceptEdits 快路径：先检查命令在 acceptEdits 模式下是否会被允许，如果是则跳过昂贵的分类器调用。
  • PowerShell 特例：默认情况下 PowerShell 在 auto 模式中需要明确用户权限。
  • 连续拒绝限制：3 次连续拒绝或 20 次总拒绝后回退到人工审批。
  • 断电器（Circuit Breaker）：GrowthBook 动态配置可全局禁用 auto 模式。
  • safetyCheck 豁免：非分类器可审批的安全检查（如跨机器消息）免疫 auto 自动批准。
  • fail-closed/fail-open：分类器不可用时，取决于 GrowthBook 配置。

6.3 模式转换

transitionPermissionMode(fromMode, toMode):
  1. from plan → not-plan: setHasExitedPlanMode(true)
  2. 进入 auto:
     - 设置 autoModeActive = true
     - stripDangerousPermissionsForAutoMode()
  3. 离开 auto (或从 auto 进入 plan):
     - 设置 autoModeActive = false
     - restoreDangerousPermissions() 恢复危险规则
     - setNeedsAutoModeExitAttachment(true)
  4. plan 模式中切换 auto 的激活/去激活:
     - transitionPlanAutoMode() 根据 shouldPlanUseAutoMode 判断

七、权限更新与持久化

7.1 PermissionUpdate 类型

所有权限变更都通过统一的 PermissionUpdate 数据结构表达：

  • addRules — 添加规则
  • replaceRules — 替换规则
  • removeRules — 删除规则
  • setMode — 设置模式
  • addDirectories / removeDirectories — 管理目录权限

7.2 执行与持久化

applyPermissionUpdate() 修改内存中的 ToolPermissionContext。 persistPermissionUpdate() 将可持久化的更新写入 settings JSON 文件。 PermissionUpdateSchema.ts 使用 Zod 确保更新格式正确性。

八、Hook 集成

权限系统通过 PermissionRequest hook 类型与 Claude Code 的 Hook 系统集成。 每个工具调用前会触发 executePermissionRequestHooks()， Hook 可以返回 allow（带可选 input 修改和规则更新）、deny（带可选 interrupt）或继续。

Hook 在两种场景下运行：

  • Headless Agent：在 permissions.ts 的 runPermissionRequestHooksForHeadlessAgent() 中，在 auto-deny 前给 Hook 一次机会。
  • 交互式 Agent：在 interactiveHandler.ts 中，对话框显示后异步并行执行。
  • Coordinator Worker：在 coordinatorHandler.ts 中，顺序等待。

九、权限解释器

permissionExplainer.ts 使用 Claude API（Haiku 模型）为每个权限请求生成人类可读的解释， 展示在对话框中帮助用户理解"什么命令"、"为什么执行"、"有什么风险"。

使用 sideQuery() 带强制 tool_choice 的结构化输出，返回包含 riskLevel（LOW/MEDIUM/HIGH）、 explanation（命令说明）、reasoning（执行动机）、risk（风险描述）的结构化数据。 可通过 permissionExplainerEnabled 配置关闭。

十、审计日志与遥测

所有权限决定通过 permissionLogging.ts 集中记录：

  • Analytics 事件：Statsig 事件 tengu_tool_use_granted_* 和 tengu_tool_use_rejected_*
  • OTel 遥测：tool_decision OTel 事件
  • 代码编辑计数器：对 Edit/Write/NotebookEdit 工具的决策单独追踪，按语言分类
  • 上下文记录：toolUseContext.toolDecisions Map 保存每个 tool_use 的决策历史

十一、核心数据结构

// ToolPermissionContext - 权限上下文的"事实来源"
type ToolPermissionContext = {
  mode: PermissionMode                    // 当前权限模式
  additionalWorkingDirectories: Map       // 额外工作目录
  alwaysAllowRules: ToolPermissionRulesBySource  // allow 规则（按来源分组）
  alwaysDenyRules: ToolPermissionRulesBySource   // deny 规则
  alwaysAskRules: ToolPermissionRulesBySource    // ask 规则
  isBypassPermissionsModeAvailable: boolean
  strippedDangerousRules?: ToolPermissionRulesBySource  // auto 模式剥离的危险规则
  shouldAvoidPermissionPrompts?: boolean   // headless 标记
  isAutoModeAvailable?: boolean
  prePlanMode?: PermissionMode            // 进入 plan 前的模式
}

// PermissionDecision - 最终权限决策
type PermissionDecision =
  | { behavior: 'allow'; updatedInput?; decisionReason? }
  | { behavior: 'ask'; message; suggestions?; blockedPath? }
  | { behavior: 'deny'; message; decisionReason }

// PermissionDecisionReason - 决策原因（审计关键）
type PermissionDecisionReason =
  | { type: 'rule'; rule: PermissionRule }
  | { type: 'mode'; mode: PermissionMode }
  | { type: 'subcommandResults'; reasons: Map }
  | { type: 'hook'; hookName; reason? }
  | { type: 'classifier'; classifier; reason }
  | { type: 'safetyCheck'; reason; classifierApprovable }
  | { type: 'sandboxOverride'; reason }
  | { type: 'workingDir'; reason }
  | { type: 'asyncAgent'; reason }
  | { type: 'other'; reason }

十二、总结

Claude Code 的权限系统是一个多层次、可扩展的安全架构，核心设计目标是在"不打断用户"和"确保安全"之间取得平衡：

  • 规则系统提供灵活的工具级和内容级权限配置，支持从个人 setting 到企业策略的多个规则来源。
  • 模式系统让用户一键切换安全姿态，从完全信任（bypass）到完全保护（dontAsk），再到 AI 辅助的 auto 模式。
  • 决策流水线确保每个工具调用经过严格的判定级联，不存在安全缺口。
  • 交互模型通过多路竞速（本地 Terminal + CCR Bridge + Channel + Hook + Classifier）让审批尽可能快速流畅。
  • Auto 模式代表了最先进的安全自动化：用 AI 分类器替代人工审批，同时保有多层安全护栏避免误放行。
  • 审计日志确保每个决策都可追溯、可分析。
