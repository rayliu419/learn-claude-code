Claude Code Agent Teams / Swarm 系统设计分析

多 Agent 团队协作框架：持久队友、邮箱通信、三种执行后端、权限代理

~/.claude/teams/<name>/config.json 三层身份解析 四种执行模式 结构化协议消息

一、总览

Claude Code 的 Swarm 系统是一套多 Agent 团队协作框架，支持 Leader 创建团队、Spawn 持久队友、通过 Mailbox 互通消息、通过 Coordinator 模式编排异步 Worker。它从教学 demo 的 teammate + inbox + independent loop 三层模型演进到完整的生产级实现，涵盖三种执行后端（tmux / iTerm2 / in-process）、文件锁通信、权限代理协调和运行模式自动检测。

二、核心数据结构

TeamFile — 团队注册中心

团队配置文件是系统的中枢：

TeamFile { name: string // 团队名 description?: string // 描述 createdAt: number leadAgentId: string // 确定性 Agent ID: "team-lead@{teamName}" leadSessionId?: string // 实际 Session UUID hiddenPaneIds?: string[] // 已隐藏的 tmux 面板 teamAllowedPaths?: [] // 团队级别路径权限白名单 members: [{ agentId: string // "alice@my-team" name: string // "alice" model?: string // 模型覆盖 color?: string // UI 颜色 planModeRequired?: boolean tmuxPaneId: string cwd: string worktreePath?: string // 可选 git worktree 隔离 sessionId?: string subscriptions: string[] backendType?: BackendType isActive?: boolean // false = idle, undefined/true = active mode?: PermissionMode }] }

设计要点：团队状态完全通过共享磁盘的 config.json 同步，不需要 Leader 主动心跳。ssLeader 和 teammate 各自读写同一份文件。

Teammate 身份（三层优先级）

优先级机制来源场景
1AsyncLocalStoragerunWithTeammateContext()In-process 队友
2dynamicTeamContextCLI args (--agent-id)tmux/iTerm2 队友
3环境变量CLAUDE_CODE_AGENT_ID旧版兼容

关键设计原则：isTeammate() 对 Leader 返回 false。Leader 不应拥有 teammate 的行为（心跳、邮箱轮询）。Leader 的身份通过 formatAgentId('team-lead', teamName) 确定，但保持 isTeammate() 返回 false 以避免副作用。

存储与并发安全

存储路径: .claude/teams/{team_name}/inboxes/{agent_name}.json 格式: JSON 数组 [TeammateMessage] 写入流程: writeToMailbox(recipient, message) ├─ ensureInboxDir() ← 创建 inbox 目录 ├─ lockfile.lock(inboxPath) ← proper-lockfile（10次重试, 5-100ms退避） ├─ re-read messages ← lock 后重读（避免竞态） ├─ messages.push(newMessage) ├─ writeFile() ← 写回磁盘 └─ lockfile.release() 关键结构体: TeammateMessage { from: string // 发件人 text: string // 消息内容（结构化协议时为 JSON stringify 后的协议对象） timestamp: string // ISO 时间戳 read: boolean // 是否已读 color?: string // 发件人颜色 summary?: string // 5-10 字预览摘要 }

四、Coordinator 模式

Coordinator 模式是不同于 Swarm 的多 Agent 编排方式——通过 AgentTool 起 worker，通过 SendMessageTool 继续 worker。

Coordinator 系统提示词核心规则

  • 角色约束：Coordinator 负责"分解 → 派发 → 综合 → 再派发"，不直接执行工具
  • Worker 独立性：每个 worker prompt 必须是自包含的——Worker 看不到 Coordinator 的对话历史
  • 并行优先：将独立 task 并行发给多个 worker（research、implementation、verification）
  • 合成最重要：Worker 完成后，Coordinator 必须阅读 findings，形成具体的实现规格
  • 验证独立性：Verification worker 应"新鲜视角"审查代码，不继承前 worker 的 context

Coordinator Workflow 示例

User: "Auth module 有个 null pointer, 帮忙修一下" Coordinator: ├─ AgentTool("Investigate auth bug", subagent: "worker") └─ AgentTool("Research auth tests", subagent: "worker") → "从两个角度研究，稍后汇报" User (task-notification): → [worker A 完成: 在 validate.ts:42 发现 null pointer] Coordinator: └─ SendMessage(worker A, "在 validate.ts:42 加 null check... Commit 并报告 hash") → "修复进行中" User: "怎么样了?" Coordinator: → "新 test 的修复在跑，等 test suite 的结果"

Worker 权限代理

Worker 遇到权限弹窗 │ ├─ 尝试 Bash 分类器自动批准 │ ↓ 失败 └─ createPermissionRequest() ├─ 创建 permission_request ├─ writeToMailbox(leader, request) ← 写入 Leader 的 inbox └─ registerPermissionCallback() ← 注册回调等待响应 Leader useSwarmPermissionPoller ├─ 轮询自己的 inbox ├─ 检测到 permission_request ├─ 用户批准/拒绝 → writeToMailbox(worker, response) ← 写入 Worker 的 inbox └─ UI 显示处理结果 Worker ├─ 轮到自己 inbox → 读到 permission_response └─ resolve 回调 → 继续/拒绝执行

六、关键设计决策

决策选择理由
Team 状态存储共享磁盘 JSON 文件不需要 Leader 主动心跳，任何 teammate 重启后都能通过配置文件恢复状态
通信方式文件邮箱 + 锁解耦消息收发，支持跨进程通信（tmux），无需网络 RPC
In-process 隔离AsyncLocalStorage共享进程资源（API client、MCP）同时隔离身份，避免全局变量冲突
AbortController独立不链接 parentLeader query 中断时 teammate 继续工作，避免级联取消
Leader 身份formatAgentId('team-lead', teamName) 但 isTeammate() = false有确定性 ID 供 teammate 发消息，但不触发 teammate 的副效应
Coordinator vs Swarm两套独立编排模式Coordinator 适合短生命周期 worker 编排，Swarm 适合长生命周期 teammate 协作
权限代理Mailbox 转发用户只需在一个界面（Leader）处理所有权限，无需每个 teammate 弹窗
后端回落tmux → iTerm2 → in-process确保在任何终端环境下都能使用 swarm，自动检测无需用户配置

八、总结

Swarm 系统设计哲学："配置文件优先 + 文件通信 + 三层身份 + 环境自适应执行。"

整个系统没有中心化的团队状态服务器。所有团队状态通过共享磁盘的 config.json 同步；所有通信通过文件邮箱加锁完成；teammate 身份通过 AsyncLocalStorage → dynamicTeamContext → 环境变量三层解析；执行后端通过环境自动检测从 tmux 逐级回落到 in-process。

关键设计权衡

简洁性✅ 共享文件架构不需要中心服务器，tmux teammates 只需 CLI flags
并发安全⚠️ 文件锁虽安全但可能成为瓶颈（10 次重试 + 100ms 最大退避）
灵活性✅ 三种执行后端 + 自动检测 + Coordinator/Swarm 两套编排模式
隔离性✅ In-process 共享 API 连接（成本优势）；tmux 完整进程隔离（安全）
恢复能力✅ Session 恢复时通过配置文件重建 teamContext，teammate 可继续工作
可观测性✅ idle_notification + 状态树 + spinner + collapse 机制，精确呈现 swarm 状态
