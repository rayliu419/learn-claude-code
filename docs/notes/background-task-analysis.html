Claude Code 后台任务系统设计分析

从教学版 BackgroundManager 到生产级任务类型系统 + 磁盘输出管道 + 优先级通知队列

src/tasks/LocalShellTask/ 7 种任务类型 优先级通知队列 5 态状态机

一、总览

Claude Code 的后台任务系统是教学版 s13_background_tasks.py（一个简单的 threading.Thread + 内存通知队列）的生产级演化。核心变化是从"一个后台线程跑 shell"扩展为一套包含任务类型系统 + 磁盘输出管道 + 优先级通知队列 + React 状态管理的完整框架。

核心设计哲学："主循环只管往前推进，后台结果通过外部队列异步回流。"教学版的 drain_notifications() 在生产代码中演化为全局 commandQueue，所有后台结果都经由优先级队列等待主循环的下一轮处理。

关键数字

任务类型7 种（local_bash / local_agent / remote_agent / in_process_teammate / local_workflow / monitor_mcp / dream）
任务状态5 态（pending → running → completed / failed / killed）
队列优先级3 级（now / next / later），后台通知默认 later
输出磁盘上限5GB (MAX_TASK_OUTPUT_BYTES)
输出上下文上限32KB 默认，160KB 上限 (TASK_MAX_OUTPUT_LENGTH)
Stall 检测45s 无增长 + 尾部匹配交互提示模式
Assistant 自动背景化阻塞命令 > 15s 自动转入后台
ID 熵36^8 ≈ 2.8 万亿组合

三条核心设计原则

1. 分离执行与通知

后台执行只负责：产出结果到磁盘、控制状态机（running → completed/failed/killed）。通知队列只负责：将摘要 XML 带回到模型上下文。两者通过 enqueueShellNotification() 桥接。

2. 输出永不直接入上下文

完整输出走磁盘文件，通过 <output_file> 标签引用路径。上下文只放 XML 摘要通知。模型通过 Read 工具按需读取完整输出，由 formatTaskOutput() 做截断保护。

3. 单主循环 + 全局外部队列

主循环不等待后台任务。所有命令——用户输入、任务通知、孤儿权限——走同一个 commandQueue。主循环在 handlePromptSubmit() 中从队列取出最高优先级的命令进行处理。React 组件通过 useSyncExternalStore 订阅。

3.4 通知队列（commandQueue）

全局单例 commandQueue: QueuedCommand[]，优先级 + FIFO 出队：

  • now (优先级 0)：紧急命令，用户输入直接提交
  • next (优先级 1)：用户发起的常规命令，默认值
  • later (优先级 2)：后台任务通知，enqueuePendingNotification() 的默认优先级

所有命令——用户输入、任务通知、孤儿权限——都走同一个队列。非 React 代码通过 getCommandQueue() / dequeue() 直接操作；React 通过 useSyncExternalStore 订阅。

四、通知 XML 格式

后台任务完成时，生产代码通过 XML 标签结构告知模型：

<task_notification> <task_id>ba1b2c3d4</task_id> <tool_use_id>toolu_xxx</tool_use_id> <output_file>/tmp/xxx/tasks/ba1b2c3d4.output</output_file> <status>completed</status> <summary>Background command "npm run build" completed (exit code 0)</summary> </task_notification>

关键标签设计

标签用途细节
task_id唯一标识匹配原始 BashTool 返回的 backgroundTaskId
tool_use_id关联原始调用可选，存在时使模型能关联到之前的 tool_use
output_file完整输出路径模型可 Read 此文件获取完整输出
status终结状态completed / failed / killed。没有此标签的通知被 SDK 发射器跳过
summary摘要文本前缀 Background command 用于通知折叠检测

五、三种后台执行触发模式

模式 1：显式 run_in_background

模型在 BashTool 调用时设 run_in_background: true → 立即 spawnShellTask() → 返回 backgroundTaskId。最直接的路径，与教学版 BackgroundManager.run() 对应。

模式 2：前台自动背景化（auto-backgrounding）

前台命令执行超过 30s 后自动转入后台。ShellCommand.onTimeout 回调触发 startBackgrounding()，通过 backgroundExistingForegroundTask() 原位翻转 isBackgrounded: true，避免重复的 SDK 事件和泄漏的清理回调。

模式 3：Assistant 模式超时背景化

KAIROS assistant 模式下，主 agent 的阻塞命令超过 ASSISTANT_BLOCKING_BUDGET_MS = 15000ms 自动转入后台，保持 agent 的协调能力不被阻塞。

六、输出管道：从进程到模型

四层输出管道

layer 1: 进程 → 文件 (bash 模式)
子进程 stdout/stderr fd → 直接写入 .output 文件
JS 不处理原始输出流，通过文件 tail 获取进度
layer 2: DiskTaskOutput [diskOutput.ts] — 异步写入队列
append() 入队 → 单 drain 循环按序写磁盘
#queueToBuffers() 用 splice 原地释放，通知 GC
5GB 上限 (MAX_TASK_OUTPUT_BYTES)
O_NOFOLLOW 防 symlink / O_EXCL 防覆盖
layer 3: TaskOutput [TaskOutput.ts] — 内存 + 轮询
stdoutBuffer / stderrBuffer 内存缓冲
#recentLines 环形缓冲区 (1000 行)
1s 轮询文件尾 → React 进度回调
layer 4: formatTaskOutput [outputFormatting.ts] — AI 适配
模型 Read 输出时调用，默认 32KB，上限 160KB
超限时截断：[Truncated. Full output: /path] + 末尾 N 字符

增量输出读取

getTaskOutputDelta(taskId, fromOffset, maxBytes) │ ├─ readFileRange(outputPath, fromOffset, maxBytes) │ └─ 只从指定偏移读指定大小，不加载完整文件 │ ├─ 返回 { content, newOffset } │ └─ content: 新增内容 │ └─ newOffset: 下一次读取的起始偏移 │ └─ ENOENT → 返回 ''（文件尚不存在，等下一轮）

这个设计解决了教学版"每次全量读文件"的问题：通过游标 outputOffset 实现增量读取，避免每次 POLL 都加载完整文件。特别是在 generateTaskAttachments() 中，每轮只读 delta 内容。

七、通知折叠机制

教学版没有的功能——当多个后台 bash 任务连续完成时，生产代码会将成功通知合并：

collapseBackgroundBashNotifications(messages) │ ├─ 遍历 messages，寻找连续的成功任务通知 │ 条件: type=user, status=completed, summary 以 │ "Background command " (BACKGROUND_BASH_SUMMARY_PREFIX) 开头 │ ├─ 找到 N 条连续匹配 → 合为 1 条: │ │ completed │ N background commands completed │ │ └─ 失败的 / 被杀死的任务保持独立，不参与折叠

Monitor 类型任务有自己的 prefix（Monitor "...），不参与 bash 折叠。Verbose 模式（Ctrl+O）下跳过折叠，每条通知独立显示。

八、Stall 探测

教学版有一个简单的 detect_stalled(45s) 超时标记。生产版本演化为智能的交互输入提示检测：

startStallWatchdog(taskId, description, kind, toolUseId, agentId) │ ├─ 每 5s 检查输出文件大小 (STALL_CHECK_INTERVAL_MS) │ ├─ 大小增长 → reset 计时器 │ └─ 45s (STALL_THRESHOLD_MS) 无增长 → 读尾部 1024 字节 │ ├─ looksLikePrompt(tail) 模式匹配: │ /\(y\/n\)/i, /\[y\/n\]/i, /\(yes\/no\)/i │ "Are you sure?", "Press any key", "Continue?", │ "Overwrite?", "Shall I", "Would you" │ ├─ 匹配 → 发送不含 标签的告警通知 │ (SDK 发射器跳过，仅做提示) │ └─ Monitor kind 跳过（monitor 是流式退出）

这种设计比简单的超时标记更智能：只在外观像交互提示时才告警，长时间编译（git log -S、大型构建）不会误触发。

九、资源泄漏防护

生产代码解决了教学版未处理的资源泄漏问题：

9.1 按 Agent 的孤儿清理

killShellTasksForAgent(agentId, getAppState, setAppState) │ ├─ 遍历 AppState.tasks │ └─ isLocalShellTask && task.agentId === agentId && running │ → killTask(taskId, setAppState) │ └─ dequeueAllMatching(cmd => cmd.agentId === agentId) └─ 清空该 agent 的待处理通知

9.2 任务输出生命周期

操作影响
initTaskOutput()O_WRONLY | O_CREAT | O_EXCL | O_NOFOLLOW 创建空文件
appendTaskOutput()异步追加内容到文件
flushTaskOutput()等待所有排队写入完成
evictTaskOutput()冲刷后仅从内存 map 移除，保留磁盘文件

9.3 /clear 安全

任务输出路径在首次调用时捕获 session ID，之后缓存。即使 /clear 调用 regenerateSessionId()，已有 TaskOutput 实例仍使用旧路径，避免后台任务输出文件丢失。

十四、总结

设计哲学："主循环只管往前推进，后台结果通过外部队列异步回流。"

教学版 BackgroundManager 用 200 行 Python 展示了核心模式——后台线程 + 通知队列。生产版将其工程化为 100+ 文件、7 种任务类型、4 层输出管道、优先级通知队列的复杂系统，但核心思想不变：并行的是执行与等待，不是主循环本身。

从教学到生产的关键演化路径

1. 从单类型到类型系统 — shell → 7 种任务（agent/remote/teammate/workflow/monitor/dream），每种有自己的生命周期和 kill 逻辑。

2. 从内存列表到全局优先级队列 — 简单 list → 三优先级 FIFO + React store 兼容接口 + 通知折叠。

3. 从全量读写到增量流式管道 — 整段写文件 → 异步 drain 队列 + 游标增量读取 + 尾部轮询 + 格式化适配。

4. 从简单超时到智能 stall 检测 — 45s 标记 → 交互输入提示模式识别，只在外观像提示时触发。

5. 从无清理到完整资源生命周期 — daemon 线程 → Agent 级孤儿清理 + TOCTOU 安全 + 延迟 eviction + 跨 /clear 安全。
